一个轮次就是一条进来的消息，以及它引起的全部工作。`BubFramework` 负责一个轮次：找会话、装载状态、构建 prompt、跑模型、发出回复。每个阶段都留了 hook，插件可以改这一段。

轮次属于 `bub[app]`。直接调 `core.Agent.run()` 没有轮次：循环就用你给的 prompt、state 和 tape 开始。

## 阶段

`framework.process_inbound(message)` 按下面的顺序执行：

| 阶段 | 做什么 |
| --- | --- |
| `resolve_session` | 为收到的消息选出会话 ID。 |
| `load_state` | 从各个 hook 收集本轮状态。 |
| `build_prompt` | 把收到的内容转成 prompt。 |
| `run_model` / `run_model_stream` | 产出模型输出：完整结果，或者一个流。 |
| `save_state` | 收尾模型阶段的工作。它在自己的 `finally` 块里运行。 |
| `render_outbound` | 把结果转成出站 envelope。 |
| `dispatch_outbound` | 发出每一个出站 envelope。 |

内置插件提供应用的默认行为。其他插件可以在 hook 允许的范围内补充或替换行为。[Hooks 参考](/zh-cn/docs/reference/hooks/)定义了首个有效结果、结果合并和优先级。

## Agent 调用

内置的 `run_model_stream` hook 调用 `BubAgent.run_stream()`。`BubAgent` 用的是内核的模型与工具循环，再加上配置、skills、命令、steering 和应用的工具策略。

框架在流式与非流式 hook 结果之间做转换。`process_inbound(..., stream_output=True)` 让渠道路由器边收边处理，流结束时返回一个完整的 `TurnResult`。

插件替换 `run_model` 就会改掉这一步。比如一个 echo 插件可以直接返回文本，根本不创建 agent run。只有选中的实现真的用了内核 agent，才会产生核心事件和 tape 记录。

## 资源和失败

当 hooks 要提供存储或其他应用资源时，用 `async with framework.running():`。它打开这些资源，退出时释放。内置的单条消息 lifespan 在装载状态时打开，在 `save_state` 里关闭。

执行进到模型阶段后，`save_state` 就会运行，模型阶段抛异常也一样。会话解析、状态装载或 `build_prompt` 的失败发生在这个 `finally` 块之前，所以不会触发它。插件如果在这几个较早的阶段拿了资源，要自己释放。

内置的 `save_state` 关闭单条消息 lifespan。应用另外保存选定的设置。要保存其他状态，得自己定持久化策略。

模型阶段抛出未处理异常时，框架先跑 `save_state`，然后跳过渲染和分发。外层的错误路径调用 `on_error(stage="turn", ...)`，再把异常抛出去。内置的错误观察器可以通过出站分发发一条错误回复。某个 `on_error` 观察器失败，不影响其他观察器。

每个 Agent 都有一个事件总线（`EventBus`）。通过 `agent.events` 注册处理器，可以记录运行过程，也可以在模型或工具调用前作出决定。

## 区分三种数据 {#three-kinds}

| 类型 | 用途 | 获取方式 |
| --- | --- | --- |
| `AgentEvent` | 观察生命周期，控制模型和工具调用 | `agent.events.on(...)` |
| `StreamEvent` | 向调用方交付文本、工具进度、用量和错误 | 迭代 `agent.run()` 返回的流 |
| `TapeEntry` | 保存对话和部分运行记录 | 查询 [Tape](/zh-cn/docs/concepts/tape/) |

三者的数据流向不同：

- 修改 `AgentEvent` 的可变字段，可以影响后续执行。
- `StreamEvent` 只是输出载荷。迭代会驱动模型循环，关闭流会结束尚未完成的运行。
- `TapeEntry` 供后续查询，不会改变正在执行的 Step；只有被 `TapeContext` 选中的条目才会成为后续模型输入。

## 注册处理器 {#handlers}

```python
from bub.core.events import StepFinished, ToolCallFinished


@agent.events.on(ToolCallFinished)
async def report_tool(event: ToolCallFinished) -> None:
    print(event.call.tool, event.result.duration_ms, "ms")


def report_step(event: StepFinished) -> None:
    print("step", event.step, event.status)


agent.events.on(StepFinished, report_step)
agent.events.off(StepFinished, report_step)  # 不再需要时移除
```

装饰器和直接传函数等价。注册到基类的处理器也会接收子类事件；监听 `AgentEvent` 可以统一处理所有 Agent 事件。

### 分发规则 {#delivery}

1. 每次 `emit()` 按注册顺序调用匹配的处理器。
2. 处理器返回 awaitable 时，总线等待它完成后再调用下一个。
3. 返回值会被忽略；需要控制运行时，修改事件字段。
4. 异常会传播给 `emit()` 的调用方，可能使运行失败。
5. 每个处理器执行前检查 `event.stopped`；为 `True` 时停止本次派发。

只用于日志或指标的处理器应自行处理异常，避免影响主流程。顺序保证只作用于同一次 `emit()`；并发工具或多个 Run 共享状态时，仍需要调用方协调。

## 控制模型和工具调用 {#call-control}

`decision` 用于跳过原始调用，其他可变字段用于替换请求、参数、结果或后续消息。例如，在执行前禁止没有权限的订单修改：

```python
from bub.core.events import ToolCallDecision, ToolCallStarted


@agent.events.on(ToolCallStarted)
def check_order_update(event: ToolCallStarted) -> None:
    if event.call.tool != "update_order":
        return
    if not event.state.get("orders_writable"):
        event.decision = ToolCallDecision.deny("当前会话不允许修改订单。")
```

`ToolCallStarted` 支持三种控制方式：

| 操作 | 是否执行工具 | 结果 | 后续处理器 |
| --- | --- | --- | --- |
| `deny(message)` | 否 | 工具错误 | 停止派发 |
| `replace(result)` | 否 | 指定结果 | 停止派发 |
| 替换 `event.call` | 是，使用新调用 | 实际执行结果 | 继续派发 |

被拒绝或替换的工具仍会发出 `ToolCallFinished`。模型循环会把错误作为工具结果交回模型；直接命令则向调用方抛出错误。

事件本身是可变 dataclass，但 `event.call` 和 `event.request` 等载荷是 frozen 对象。替换参数时使用 `dataclasses.replace()` 创建新载荷，不要原地修改字段。

在 `LLMCallStarted` 上设置 `event.decision = LLMCallDecision.finish(text)` 可以跳过模型提供商，直接产生文本。此时不会发出对应的 `LLMCallFinished`。

## 记录对话与自定义事件 {#recording}

Agent 会先注册 `TapeRecorder`，再注册你的处理器。记录器订阅 `RunStarted`、`RunFinished`、`StepStarted`、`StepFinished`、`ChatFinished` 和 `CommandFinished`。

其中，`ChatFinished` 负责保存对话和工具往返，后续模型调用从这些记录构建上下文。Tracing 与 Tape 记录相互独立；关闭 tracing 不会停止记录。

自定义事件继承 `AgentEvent`，需要当前 Tape 时继承 `TapeEvent`：

```python
from dataclasses import dataclass

from bub.core.events import TapeEvent


@dataclass(kw_only=True)
class OrderReviewed(TapeEvent):
    order_id: str


@agent.events.on(OrderReviewed)
async def record_review(event: OrderReviewed) -> None:
    await event.tape.append_event("order.reviewed", {"order_id": event.order_id})


async def mark_reviewed() -> None:
    tape = agent.tape("customer-42")
    await agent.events.emit(
        OrderReviewed(state=tape.context.state, tape=tape, order_id="A123")
    )
```

`TapeRecorder` 不会自动记录自定义事件，上例由处理器显式写入。自定义事件也没有内置的 `decision` 协议；需要返回结果时，自行定义可变字段，需要提前停止派发时，覆写 `stopped` 属性。工具可以通过 `context.events` 发出事件。

## 在应用中使用 hooks {#app-plugins}

`AgentPlugins` 将应用 hooks 接到 Agent 事件：

| 应用 hook | Agent 事件 |
| --- | --- |
| `before_llm_call` / `after_llm_call` | `LLMCallStarted` / `LLMCallFinished` |
| `before_tool_call` / `after_tool_call` | `ToolCallStarted` / `ToolCallFinished` |
| `continue_prompt` | `StepFinished` |
| `provide_steering_inbox` | `MessagesPending` |

引导（Steering）通过 `MessagesPending` 把补充消息注入当前 Run 的后续模型请求。它不同于排队（Queue up）：排队消息等待当前 Turn 结束后再处理。事件层负责提供注入位置，具体准入与队列策略由渠道和应用决定。

`BubAgent` 默认使用此适配器，核心 Agent 也可以[显式接入](/zh-cn/docs/sdk/reuse-app/#other-hooks)。

两种接入方式的异常策略不同：直接 EventBus 处理器的异常向发布方传播；拦截 hook 的异常会被记录并跳过。需要拒绝调用时，应返回对应 decision。完整签名见 [Hooks 参考](/zh-cn/docs/reference/hooks/#interception-through-pluginagenthooks)，示例见[插件与 Hooks](/zh-cn/docs/app/plugins/)。

`framework.events` 是另一条独立总线，只发布应用层的 `CommandChanged`、`WorkChanged` 和 `PromptChanged`，不承载模型调用或渠道事件。

## 事件参考 {#event-reference}

| 事件 | 触发时机 | 可读取或修改的内容 |
| --- | --- | --- |
| `RunStarted` | 模型 Run 开始 | `model`、`prompt`、`metadata` |
| `RunFinished` | Run 的流关闭 | `status`、`steps`、耗时和错误 |
| `StepStarted` | Step 开始 | `step`、可选的 `prompt` |
| `StepFinished` | Step 结束 | 进度、用量；继续时设置 `next_prompt` |
| `MessagesPending` | 构建请求时，或特定 Step 结束时 | 向 `messages` 追加用户内容 |
| `LLMCallStarted` | 调用模型提供商之前 | 替换 `request`；设置 `LLMCallDecision.finish()` |
| `LLMCallFinished` | 提供商调用成功或普通异常失败 | `request` 和汇总后的 `result` |
| `ToolCallStarted` | 工具执行之前 | 替换 `call`；设置 `deny` 或 `replace` |
| `ToolCallFinished` | 工具成功、普通失败、被拒绝或被替换 | 给 `event.result.result` 赋值以替换结果 |
| `ChatFinished` | 当前 Step 的对话与工具往返可记录时 | 消息、工具往返、用量和错误 |
| `CommandFinished` | 直接命令成功或失败 | 命令、状态和输出 |

`RunFinished` 在流关闭时发出；尚未迭代就关闭的 Run 以 `cancelled` 结束，Step 数为零。模型和工具的 Finished 事件不保证覆盖取消路径，因此计费和清理不能只依赖它们。

`StepFinished.next_prompt` 设置下一个 Step 的用户消息，`MessagesPending.messages` 用于接收运行期间到达的消息。达到 `BUB_MAX_STEPS` 时，运行会抛出 `max_steps_reached` 错误。

直接命令发出工具事件和 `CommandFinished`，没有 `RunStarted` / `RunFinished`。所有 Agent 事件都有 `state`；`TapeEvent` 的子类还带有当前 `tape`。

本页是 hook 接口的完整参考。用法示例见[插件与 Hooks](/zh-cn/docs/app/plugins/)，各阶段顺序见 [Turn](/zh-cn/docs/concepts/turn/#stages)。

## 阅读约定 {#notation}

| 标记 | 含义 |
| --- | --- |
| **首个** | 按优先级调用，返回第一个非 `None` 的结果；`False`、`""`、`[]` 也是结果 |
| **全部** | 调用所有实现并收集返回值；单项失败是否影响整体取决于 hook |
| **同步** | 只能同步实现；返回 awaitable 时跳过该实现并记录 `hook.async_not_supported` |
| `Envelope` | `Any`。映射、dataclass、Pydantic model 或带属性的对象均可 |
| `TurnState` | `dict[str, Any]`，本轮 hooks、工具和事件共享 |

未标记「同步」的 hook 可以同步或异步实现。

## 优先级与分发 {#priority-and-dispatch}

Bub 用 pluggy 注册实现，再用 `HookRuntime` 统一调用。

| 规则 | 说明 |
| --- | --- |
| 注册顺序 | 内置实现（`builtin`）→ `bub` 入口点插件 |
| 优先级 | `@hookimpl(tryfirst=True)` 最先，`trylast=True` 最后 |
| 同优先级 | 后注册的实现先运行 |
| 实际遍历 | `get_hookimpls()` 反转后调用 |
| 参数注入 | 按实现的 `argnames` 挑选；只声明用到的参数 |
| 不支持 | `wrapper=True`、`hookwrapper=True` |

| 收集器 | 行为 |
| --- | --- |
| `call_first` / `call_first_sync` | 第一个非 `None` 即返回；空容器和 `False` 也算结果 |
| `call_many` / `call_many_sync` | 收集所有非跳过结果；失败是否传播取决于调用路径 |

插件报告 `bub hooks` 显示 pluggy 注册顺序，不显示运行顺序。诊断 hook 顺序时应以优先级规则和日志为准。

## Turn hooks {#turn-hooks}

以下 9 个 hook 由 `BubFramework.process_inbound()` 驱动。

| Hook | 签名 | 分发 |
| --- | --- | --- |
| `resolve_session` | `(message: Envelope) -> str` | 首个；结果为空时回退到 `channel:chat_id` |
| `load_state` | `(message: Envelope, session_id: str) -> TurnState` | 全部；按低到高优先级合并 |
| `build_prompt` | `(message, session_id, state) -> list[UserContent] \| LegacyPrompt` | 首个；结果为空时使用入站正文 |
| `run_model` | `(prompt, session_id, state) -> str` | 首个 |
| `run_model_stream` | `(prompt, session_id, state) -> AsyncStreamEvents` | 首个 |
| `continue_prompt` | `(prompt, tape: Tape, state: StreamState) -> str \| None` | 首个；`StepFinished.status == "continue"` 时调用 |
| `save_state` | `(session_id, state, message, model_output) -> None` | 全部；在模型阶段的 `finally` 中调用 |
| `render_outbound` | `(message, session_id, state, model_output) -> list[Envelope]` | 全部；展开并拼接返回值 |
| `dispatch_outbound` | `(message: Envelope) -> bool` | 全部，每条出站调用一次；返回值忽略 |

### 行为细节 {#turn-hook-details}

- `build_prompt` 返回的**第一个非 `None` 结果**会被采用；如果它是 `""` 或 `[]`，框架不再尝试后续实现，而是回退到入站正文。
- `load_state` 返回非字典的值会被忽略。`save_state` 无论模型成功、失败还是取消都会调用，前提是已经进入模型阶段。
- `run_model` 与 `run_model_stream` 实现其中一个。文本结果可转换为流，流也可收束为文本；替换模型阶段后，内置 Agent 的拦截 hooks 不会自动运行。
- 模型 hook 按插件优先级选择；同一个 hook 内仍遵循 `tryfirst` / `trylast`。
- `continue_prompt` 返回 `None` 表示直接延续对话，不添加新的用户消息。它接收 `StreamState`，不是 `TurnState`。
- `render_outbound` 全部为空或只返回空批次时，Framework 用 `model_output` 生成一条回复，沿用入站的 `channel` 和 `chat_id`。
- `dispatch_outbound` 的实现无法通过返回值阻止其他实现；需要过滤时，在 `render_outbound` 阶段处理。

所有 Turn hooks 的错误最终由 `process_inbound()` 捕获，调用 `on_error(stage="turn", ...)` 后重新抛出。模型阶段自身找不到实现或流内错误使用 `stage="run_model"`。

### 提示词内容 {#prompt-content}

`build_prompt` 返回 `list[UserContent]`：

| 元素 | 构造 |
| --- | --- |
| 文本 | `str` |
| 图片 | `republic.image(url, media_type=...)` |
| 音频 | `republic.audio(url, media_type=...)` |
| 视频 | `republic.video(url, media_type=...)` |

接收旧格式提示词的 hooks（`run_model`、`run_model_stream`、`continue_prompt`、`system_prompt`）会收到：

| 情况 | 形态 |
| --- | --- |
| 没有媒体 | `str` |
| 包含媒体 | `[{"type", "media_type", "url"}]` 内容块列表 |

旧格式字符串和内容块列表仍可传入，`to_content()` 会转换；需要转回旧格式时使用 `bub.prompt.to_legacy_prompt()`。

## 应用 hooks {#application-hooks}

以下 14 个 hook 管理配置、资源、渠道和工具，不直接属于某条消息的 Turn。

| Hook | 签名 | 分发 |
| --- | --- | --- |
| `register_cli_commands` | `(app: typer.Typer) -> None` | 全部，同步 |
| `onboard_config` | `(current_config: dict) -> dict \| None` | 全部，同步；非字典结果抛 `TypeError` |
| `provide_model_options` | `(session_id, workspace: Path \| None) -> ModelOptions \| None` | 全部；合并模型列表，保留首个 `current_model` |
| `provide_environment` | `(session_id, workspace: Path) -> Environment \| None` | 首个；每会话缓存，`running()` 退出时关闭 |
| `on_error` | `(stage: str, error: Exception, message: Envelope \| None) -> None` | 全部；观察者异常记录后跳过 |
| `system_prompt` | `(prompt, state) -> str` | 全部，同步；按低到高优先级用空行拼接非空结果 |
| `provide_tape_store` | `() -> TapeStore \| AsyncTapeStore \| None` | 首个，同步；可返回生成器 |
| `provide_lifespan` | `() -> Iterator[None] \| AsyncIterator[None] \| None` | 全部，同步；每个生成器按上下文管理器进入 |
| `provide_tape_sidecar` | `() -> TapeSidecar` | 全部，同步；按 `name` 去重，保留高优先级 |
| `provide_channels` | `(message_handler) -> list[Channel]` | 全部，同步；按 `name` 去重，保留高优先级 |
| `build_tape_context` | `() -> TapeContext` | 首个，同步；返回值不是 `TapeContext` 时抛 `TypeError` |
| `admit_message` | `(session_id, message, turn: TurnSnapshot) -> AdmitDecision \| None` | 首个；`None` 使用渠道默认调度 |
| `provide_tools` | `() -> list[Tool]` | 全部，同步；按 `name` 去重，保留高优先级 |
| `provide_steering_inbox` | `() -> SteeringInbox \| None` | 首个，同步；可返回生成器 |

### 返回类型与调用时机 {#application-hook-details}

- `onboard_config` 接收「已加载配置 + 前序实现修改」，返回的字典会合并回去。插件名过滤由 `collect_onboard_config()` 执行。
- `provide_model_options` 只提供候选。是否展示、如何保存当前模型由调用方决定。
- `provide_environment` 用于 `bash`、文件工具和代码执行。未提供时，内置实现返回 `LocalEnvironment`。
- `system_prompt` 的多个结果不会互相覆盖；高优先级实现只能追加自己的块。
- `provide_tape_store` 只在 `framework.running()` 中解析一次。作用域外 `get_tape_store()` 返回 `None`。
- `provide_lifespan` 必须返回同步或异步生成器（`yield` 一次）；进入失败会阻止整个作用域启动。
- 三个资源 provider 都不接受 `@contextmanager` / `@asynccontextmanager` 装饰后的对象；运行时会把它当成普通值。
- `provide_channels` 的 `message_handler` 是异步 `(message) -> None`。实现必须返回渠道列表，而不是单个渠道。
- `admit_message` 只决定新消息如何处理，不负责创建任务；`process`、`drop`、`follow_up`、`steer` 的效果由 `ChannelManager` 执行。
- `provide_tools` 可以重复提供同名工具；优先级最高的实现胜出，其余同名工具被忽略。
- `on_error` 是观察接口。它不能阻止原异常传播；实现自身失败只记录 `hook.on_error_failed`。

`on_error` 的 `stage` 常见值：

| `stage` | 来源 |
| --- | --- |
| `turn` | Turn 内未分类的异常，包括提示词、模型阶段和回复处理 |
| `run_model` | 没有模型实现，或流中报告错误 |
| `resolve_session` | 渠道准入前解析会话失败 |
| `admit_message` | 渠道准入判断失败 |

`admit_message` 返回 `AdmitDecision` 时，`ChannelManager` 按 `action` 处理新消息：

| `action` | 当前会话已有运行中的 Turn | 当前会话空闲 |
| --- | --- | --- |
| `process` | 立即安排新的 Turn，允许并发 | 立即安排 Turn |
| `drop` | 丢弃消息 | 丢弃消息 |
| `follow_up` | 排队（Queue up），当前 Turn 结束后按 FIFO 处理 | 立即安排 Turn |
| `steer` | 引导（Steering）当前 Turn；无法注入或未及时消费时转入待处理队列 | 立即安排 Turn |

引导用于调整当前任务，排队用于追加后续任务。`provide_steering_inbox` 提供引导消息的暂存边界，`MessagesPending` 负责把它们交给 Agent。

### 运行时资源 {#runtime-resources}

`framework.running()` 按以下顺序获取资源：

1. 进入所有 `provide_lifespan` 返回的生成器。
2. 获取 `provide_tape_store` 的结果。
3. 获取 `provide_steering_inbox` 的结果。

退出时关闭会话执行环境，并按相反顺序释放上述资源；异常路径同样执行清理。

| 场景 | 作用域 |
| --- | --- |
| `bub run` | 一条消息 |
| `bub chat` / `bub gateway` | 整个应用运行期 |
| 嵌入宿主 | 由宿主决定，应覆盖服务生命周期 |

- 需要清理的 provider 应返回生成器，在 `finally` 中释放连接。
- `save_state` 只负责应用状态，不负责资源清理。
- 同一 Framework 不应重叠进入多个 `running()` 作用域。
- 后台 shell 的进程树终止规则：POSIX 先 `SIGTERM` 再 `SIGKILL`；Windows 只终止直接 shell。宿主强杀进程时仍需自行清理。
- Sidecar 的物理 Tape 名为 `<主 tape>__sidecar__<sidecar>`，随主 Tape 分支、合并、归档和重置。移除 provider 不会删除已有数据。

#### 应用错误 {#runtime-errors}

`on_error` 在该作用域内观察框架错误。它不是恢复机制，也不会改变异常的传播。嵌入宿主应自行捕获 `process_inbound()` 抛出的异常。CLI 的未处理异常通常以非零状态退出，但 `bub run` 对某些模型阶段错误只记录日志并返回回退文本，此时仍可能以 `0` 退出。
## Agent 拦截 hooks {#interception-through-pluginagenthooks}

这四个 hook 由 `AgentPlugins` 订阅 Agent 事件后调用，也可以直接由 [`PluginAgentHooks`](#pluginagenthooks) 接入。

| Hook | 签名 | 分发 |
| --- | --- | --- |
| `before_llm_call` | `(request: LLMCallRequest, state) -> LLMCallRequest \| LLMCallDecision \| None` | 链式；替换请求继续，`finish(text)` 终止 |
| `after_llm_call` | `(request, result: LLMCallResult, state) -> None` | 全部 |
| `before_tool_call` | `(call: ToolCall, state) -> ToolCallDecision \| None` | 链式；`replace` 或 `deny` 终止 |
| `after_tool_call` | `(call, result: ToolCallResult, state) -> None` | 全部；共享同一个可变结果 |

### 控制语义 {#interception-semantics}

- `before_llm_call` 返回修改后的 `LLMCallRequest` 后，后面的实现会看到新值。使用 frozen dataclass 的 `dataclasses.replace()` 创建副本。
- `LLMCallDecision.finish(text)` 跳过模型提供商，直接把 `text` 作为模型输出。它不会触发 `after_llm_call`。
- `ToolCallDecision.proceed(arguments)` 修改参数并继续；`replace(result)` 和 `deny(message)` 跳过工具并停止后续拦截实现。
- 拦截实现抛异常时会被记录为 `hook.agent_hook_failed` 并跳过。工具调用不会被异常阻止；必须返回 decision。
- 返回类型不符会记录 `hook.agent_hook_bad_return` 并跳过该实现。
- `after_llm_call` 与 `after_tool_call` 覆盖成功和普通异常失败。取消、消费方关闭流不触发。
- `after_tool_call` 也接收被拒绝和替换的调用。给 `result.result` 赋值会改变模型看到的结果；`result.error` 保留原始错误。

### 载荷字段 {#interception-payloads}

| 类型 | 字段 |
| --- | --- |
| `LLMCallRequest` | `run_id`, `model`, `messages`, `tool_names`, `max_tokens` |
| `LLMCallResult` | `run_id`, `text`, `tool_calls`, `usage`, `error`, `duration_ms` |
| `LLMCallDecision` | `action="finish"`, `text` |
| `ToolCall` | `run_id`, `tool`, `arguments`, `context` |
| `ToolCallResult` | `run_id`, `tool`, `arguments`, `result`, `error`, `duration_ms` |
| `ToolCallDecision` | `action`（`proceed` / `replace` / `deny`）、`arguments`、`result`、`message` |

`LLMCallRequest` 只暴露工具名称，不能通过它增删工具。修改工具集应在 `Agent.prepare_tools()` 或应用工具策略中完成。

### PluginAgentHooks {#pluginagenthooks}

`PluginAgentHooks` 把 Agent 事件转换为上述 hooks：

| Agent 事件 | Hook |
| --- | --- |
| `LLMCallStarted` | `before_llm_call` |
| `LLMCallFinished` | `after_llm_call` |
| `ToolCallStarted` | `before_tool_call` |
| `ToolCallFinished` | `after_tool_call` |

直接 EventBus 处理器和拦截 hooks 的异常策略不同：

| 项 | 拦截 hook | EventBus 处理器 |
| --- | --- | --- |
| 异常 | 记录后跳过 | 向 `emit()` 调用方传播 |
| 控制方式 | 返回 decision | 修改事件字段 |
| 执行顺序 | 由 pluggy 优先级决定 | 按处理器注册顺序 |

`PluginAgentHooks.subscribe(events)` 会把适配器接到现有总线或新总线。`AgentPlugins.attach(agent)` 会自动订阅，并把 `continue_prompt`、引导收件箱（`SteeringInbox`）和系统提示词接入 Agent。

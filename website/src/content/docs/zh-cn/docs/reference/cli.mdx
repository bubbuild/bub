`bub` 命令由应用层提供，需要 [安装](/zh-cn/docs/getting-started/install/) `app` 可选依赖。本页只列出内置命令；插件可以通过 `register_cli_commands` 增加命令，以 `bub --help` 和插件文档为准。

## 全局选项 {#global-options}

```text
bub [OPTIONS] COMMAND [ARGS]...
```

| 选项 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `--workspace`, `-w` | 路径 | 当前工作目录 | 设置 `BubFramework.workspace` |
| `--help` | 开关 | — | 显示帮助 |

`--workspace` 影响工具的工作目录、技能发现和相对路径解析。它不会改变 `BUB_HOME` 或配置文件位置。

命令在加载 CLI 之前先检查 `app` 可选依赖。缺少时，进程打印缺少的包和安装命令后退出，不会进入 Typer 帮助页。

## `bub run` {#bub-run}

处理一条消息的完整 Turn：解析会话、构建提示词、调用模型与工具、保存状态并生成回复，然后把 `TurnResult.outbounds` 打印到 stdout。不启动渠道管理器。

```text
bub run [OPTIONS] MESSAGE
```


| 参数 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `MESSAGE` | 文本 | 必填 | 消息正文；以命令前缀开头时执行命令 |
| `--channel` | 文本 | `cli` | 入站渠道名 |
| `--chat-id` | 文本 | `local` | 入站聊天 ID |
| `--sender-id` | 文本 | `human` | 写入 `context.sender_id` |
| `--session-id` | 文本 | `<channel>:<chat-id>` | 显式覆盖会话 ID |

输出格式：

```text
[channel:chat_id]
<正文>
```

示例：

```bash
bub run "Summarize this repository."
bub run --channel web --chat-id demo "Continue the previous topic."
bub run --session-id shared:demo ",tape.info"
```

因为不启动 `ChannelManager`：

- 不会启动 `mcp.lifecycle`、`acp-server` 等渠道或后台服务；
- 不会自动发送模型回复到聊天平台；
- 仍会执行 `provide_tape_store`、`provide_lifespan` 和 `provide_steering_inbox` 的资源作用域；
- 模型阶段使用非流式 `HookRuntime.run_model`。

模型没有返回文本时，`run` 打印入站正文或提示词文本作为回退，并记录 `run_model` 阶段错误；进程本身通常仍以退出码 `0` 结束。需要根据失败做脚本判断时，检查 stderr 和实际输出，而不只看退出码。

## `bub chat` {#bub-chat}

启动交互式 REPL。固定启用 `cli` 渠道，并附加已启用的 `Lifecycle` 渠道。

```text
bub chat [OPTIONS] [INITIAL_PROMPT]
```


| 参数 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `INITIAL_PROMPT` | 文本 | — | REPL 启动后立即提交 |
| `--chat-id` | 文本 | `local` | CLI 聊天 ID |
| `--session-id` | 文本 | `cli_session` | 会话 ID |

`chat` 强制流式输出，忽略 `BUB_STREAM_OUTPUT`。附加的 Lifecycle 让 MCP 工具和 ACP 后台服务可以在聊天中工作。

没有 `cli` 渠道时，命令打印错误并以退出码 `1` 结束。插件替换或移除了 CLI 渠道时会遇到这种情况。

```bash
bub chat
bub chat "What changed in this repository?"
bub chat --session-id shared:demo
```

在 REPL 中，逗号前缀命令由 `BUB_COMMAND_PREFIX` 决定，默认是 `,`。输入 `,help` 查看当前命令。

## `bub gateway` {#bub-gateway}

启动渠道管理器，常驻运行已启用的渠道。

```text
bub gateway [OPTIONS]
```


| 选项 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `--enable-channel` | 文本，可重复 | 空，读取 `BUB_ENABLED_CHANNELS` | 限定或排除渠道 |
| `--install` | 开关 | 关闭 | 安装并启动当前用户的后台服务 |
| `--uninstall` | 开关 | 关闭 | 停止并卸载后台服务 |

`--install` 与 `--uninstall` 互斥；同时传入会以参数错误退出。

### 渠道选择 {#channel-selection}

`BUB_ENABLED_CHANNELS` 使用逗号分隔；`--enable-channel` 可以重复，命令行值优先。

| `enabled_channels` | 结果 |
| --- | --- |
| `all` | 所有 `enabled` 且不属于 `Interface` 的渠道，减去 `!name` |
| 显式普通渠道 | 列表中 `enabled` 且未被排除的渠道 |
| 显式普通渠道 + Lifecycle | 先选择普通渠道，再附加所有已启用的 `Lifecycle` |
| 只有 Lifecycle | 只启动这些 Lifecycle |
| 只有 `!name` | 没有包含项，启动失败 |

- `Interface` 是需要用户显式选择的界面，例如 `cli`。
- `Lifecycle` 是后台服务，例如 `mcp.lifecycle`、`agent-plugins.mcp`。
- 显式选择普通渠道时，Lifecycle 默认自动附加；用 `!name` 排除。
- 没有可启用渠道时打印 `No channels are enabled...` 并以退出码 `1` 结束。

```bash
bub gateway
bub gateway --enable-channel telegram
bub gateway --enable-channel telegram --enable-channel discord
bub gateway --enable-channel telegram --enable-channel '!mcp.lifecycle'
```

排除项要加引号，避免 shell 把 `!` 当作历史展开。

### 后台服务 {#gateway-service}

| 平台 | 安装方式 | 位置或行为 |
| --- | --- | --- |
| Linux | systemd 用户单元 | `${XDG_CONFIG_HOME:-~/.config}/systemd/user/bub-gateway.service` |
| Windows | 计划任务 | 任务名 `Bub Gateway`，当前用户登录时启动 |
| macOS | 不支持 `--install` | 使用 launchd、tmux 或容器部署 |

Linux 单元使用 `Restart=on-failure`、`RestartSec=5s` 和 `WantedBy=default.target`。安装会执行 `daemon-reload`、`enable` 和 `restart`。

- 服务固定当前 Python 解释器、工作区和显式 `--enable-channel` 参数。
- 更换虚拟环境、移动工作区或改变渠道参数后，重新执行 `bub gateway --install`。
- Linux 注销后仍要运行，执行 `loginctl enable-linger "$USER"`。
- 重复安装会替换现有单元或任务并重启。
- `--uninstall` 在服务不存在时也视为成功。

macOS 没有内置服务安装路径；[部署](/zh-cn/docs/app/deploy/)提供了容器方案。

## `bub onboard` {#bub-onboard}

交互式生成配置：收集模型和插件选项，写入 `BubFramework.config_file`，默认 `~/.bub/config.yml`。不启动渠道。

```text
bub onboard [OPTIONS] [PLUGIN_NAME]
```


| 参数 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `PLUGIN_NAME` | 文本 | 无 | 只运行该插件的 `onboard_config` |

不带插件名时，先运行内置模型配置，再运行其他已注册插件的配置；指定插件名时只运行选定实现，并跳过网关服务安装询问。

| 退出码 | 含义 |
| --- | --- |
| `0` | 已保存，或用户拒绝安装网关 |
| `1` | 配置校验、写入、插件解析或网关安装失败 |

常见写入行为：

| 选择或操作 | 结果 |
| --- | --- |
| OpenAI 兼容服务或本地端点 | 写入 `openai:<model>`、`api_base`，并设置 `client_args.api_format: chat` |
| 选择 OpenAI 官方 API 但地址不是官方地址 | 地址重置为 `https://api.openai.com/v1` |
| Base URL 留空 | 保留提供商默认地址，不写入显式空值 |
| Base URL 显式输入 | 即使等于默认值也写入 |
| API key 留空 | 保留当前地址的 key，或继续使用环境变量 |
| Base URL 改变 | 清空此前填写的 key |
| 选择 Codex | 跳过模型发现，手动输入模型 ID |

连接检查只调用模型列表端点，不发起生成请求，超时 10 秒。模型是否支持工具调用不会在这一步验证。

`onboard_config` 的实现收到「当前配置 + 前序 hook 的修改」，返回字典后合并；返回非字典会抛 `TypeError`。全部实现结束后经过 `configure.validate` 才写盘。

## `bub install` {#bub-install}

安装插件到 Bub 管理的 uv 项目；不带参数时同步该项目。不启动渠道。

```text
bub install [OPTIONS] [SPECS]...
```


| 参数 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `SPECS` | 位置参数 | 空 | 要安装的包或 Git 来源 |
| `--project` | 路径 | `$BUB_HOME/bub-project` 或 `~/.bub/bub-project` | 插件项目目录；也可用 `BUB_PROJECT` |

包规格解析：

| 写法 | 解析为 |
| --- | --- |
| `package` | PyPI 包名 |
| `package@ref` | `bub-contrib` 的 `packages/package` 子目录，固定到 `ref` |
| `owner/repo` | `https://github.com/owner/repo.git` |
| `https://github.com/owner/repo.git@ref` | 带前缀的 Git URL，保留 ref |
| `git@...` 或 `https://...` | 加 `git+` 前缀 |

为任意 GitHub 仓库固定版本时，使用完整 URL：

```bash
bub install https://github.com/owner/repo.git@v1.2.0
```

不要写 `owner/repo@v1.2.0`：当前解析只接受不带 ref 的 `owner/repo` 简写。Bub 自身的仓库名也不等于包名，安装插件时以插件 README 给出的规格为准。

示例：

```bash
bub install bub-mcp@main
bub install bub-discord
bub install https://github.com/owner/repo.git@v1.2.0
bub install
```

首次调用会创建 `bub-project`：

```text
uv init --bare --name bub-project --app
uv add --active --no-sync --extra app <当前 Bub 的来源>
```

当前 Bub 的来源可能是 editable 路径、本地路径、VCS URL 或 PyPI 名称；因此从源码安装和从 PyPI 安装会得到不同的项目声明。

后续 uv 调用：

| 命令 | uv 调用 |
| --- | --- |
| `bub install`（无规格） | `uv sync --active --inexact` |
| `bub install <specs>` | `uv add --active <requirements>` |
| `bub uninstall <packages>` | `uv remove --active <packages>` |
| `bub update` | `uv sync --active --upgrade --inexact` |
| `bub update <packages>` | `uv sync --active --inexact --upgrade-package ...` |

前置条件：

- `uv` 在 `PATH`、当前 Python scripts 目录或 `~/.local/bin`；
- Bub 运行在虚拟环境中（`sys.prefix != sys.base_prefix`）；
- 显式传入的 `--project` 目录必须存在。

不满足时命令以退出码 `1` 结束。uv 失败时返回 uv 的退出码。

## `bub uninstall` {#bub-uninstall}

从托管项目卸载一个或多个插件。不启动渠道。名称必须与项目声明一致。

```text
bub uninstall [OPTIONS] PACKAGES...
```

```bash
bub uninstall bub-discord
```


只修改 `bub-project`，不修改系统 Python 或 Bub 自身所在环境中的其他包。`install`、`uninstall`、`update` 都接受 `--project`，也可以用 `BUB_PROJECT` 指定同一个目录。

## `bub update` {#bub-update}

升级托管项目中的插件；不带包名时升级全部依赖，带包名时只升级指定包。不启动渠道。

```text
bub update [OPTIONS] [PACKAGES]...
```

```bash
bub update
bub update bub-mcp
```

升级不会自动迁移插件配置或 Tape 数据。
跨版本升级后，重启 `bub chat` 或 `bub gateway`，并检查 `bub hooks` 中是否仍有入口点加载失败。

## `bub login codex` {#bub-login-codex}

通过 Codex CLI 配置 ChatGPT 套餐凭据。不启动渠道。

```text
bub login codex [OPTIONS]
```

| 选项 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `--executable` | 文本 | `codex` | Codex CLI 可执行文件 |
| `--device-auth` | 开关 | 关闭 | 使用设备授权流程 |
| `--codex-home` | 路径 | `$CODEX_HOME` 或 `~/.codex` | 凭据目录 |

成功后输出：

```text
login: ok
account_id: <id>
Use BUB_MODEL=codex:<model> for ChatGPT plan access.
```

配套配置：

```bash
export BUB_MODEL=codex:<model>
```

不要同时设置 `BUB_API_KEY`。失败时输出 `login: failed: ...` 并以退出码 `1` 结束。凭据通常写入 `$CODEX_HOME/auth.json` 或 `~/.codex/auth.json`。

## `bub hooks` {#bub-hooks}

打印 hook 实现映射。隐藏命令，不在 `bub --help` 中列出，也不启动渠道。

```text
bub hooks
```

每行格式：

```text
<hook>: <implementation>, <implementation>
```


实现按 pluggy 注册顺序输出，hook 名按字母排序。没有实现时输出 `(no hook implementations)`。

这里的顺序不是执行顺序。Bub 会反转 pluggy 的内部列表，再应用 `tryfirst` / `trylast`；诊断实际顺序见[优先级与分发](/zh-cn/docs/reference/hooks/#priority-and-dispatch)。

## 退出码 {#exit-codes}

| 场景 | 退出码 |
| --- | --- |
| 命令成功 | `0` |
| Typer 参数错误 | `2` |
| 缺少 `app` 可选依赖 | `1`，进程在 Typer 前退出 |
| 没有可启用渠道、插件失败、配置失败 | `1` |
| `bub install` / `uninstall` / `update` 的 uv 失败 | uv 的退出码 |

`bub run` 的模型错误可能只写入日志并返回回退文本，因此不能只依赖退出码判断模型调用是否成功。

title: 部署
description: 用 Docker Compose 运行 Bub 网关，持久化数据并安全升级。
---

Bub 可以作为常驻容器运行。官方镜像已包含运行时、常用命令行工具和托管插件环境；宿主机只需要提供 `.env`、工作区和数据目录。

两种起步方式：

- **使用发布镜像**：下载仓库中的 [`docker-compose.yml`](https://github.com/bubbuild/bub/blob/main/docker-compose.yml) 和 [`env.example`](https://github.com/bubbuild/bub/blob/main/env.example)，不需要源码。
- **本地构建**：从 [GitHub Releases](https://github.com/bubbuild/bub/releases) 获取源码归档，或克隆仓库，再使用同一份 Compose 文件构建。

镜像由仓库中的 [`Dockerfile`](https://github.com/bubbuild/bub/blob/main/Dockerfile) 和 [`entrypoint.sh`](https://github.com/bubbuild/bub/blob/main/entrypoint.sh) 定义。

## 开始之前 {#before-you-start}

- 安装 Docker 与 Compose v2，并确认 `docker compose version` 可用。
- 准备模型配置。`.env` 至少包含 `BUB_MODEL`，以及 `BUB_API_KEY` 或提供商专用 key；字段说明见[配置](/zh-cn/docs/app/configure/)。
- 如果要运行 Telegram 网关，准备 `BUB_TELEGRAM_TOKEN` 和一份用户或群组白名单，见[Telegram 网关](/zh-cn/docs/app/gateway/#telegram)。

容器会以 `root` 运行。若宿主机目录由其他用户创建，先确认 Docker 进程能读写对应路径。

## 1. 准备配置 {#configure}

在 Compose 文件所在目录创建 `.env`：

```bash
cp env.example .env
```

最小 Telegram 配置：

```bash
BUB_MODEL=openrouter:openrouter/free
BUB_API_KEY=sk-or-...
BUB_TELEGRAM_TOKEN=123456:abcdef...
BUB_TELEGRAM_ALLOW_USERS=123456789
```

生产环境应同时设置 `BUB_TELEGRAM_ALLOW_CHATS` 或 `BUB_TELEGRAM_ALLOW_USERS`。留空白名单会让任何能找到机器人的人发起会话。

`docker compose` 会读取 `.env` 并传给容器。不要把含有 token 的 `.env` 提交到仓库。

## 2. 了解挂载 {#volumes}

默认 Compose 使用三个绑定挂载：

```yaml
volumes:
  - ${BUB_WORKSPACE_PATH:-.}:/workspace
  - ${BUB_HOME_HOST:-${HOME}/.bub}:/data
  - ${BUB_AGENT_HOME:-${HOME}/.agents}:/root/.agents
```

| 容器路径 | 内容 | 宿主机变量 |
| --- | --- | --- |
| `/workspace` | Bub 的工具以这里为工作目录 | `BUB_WORKSPACE_PATH`，默认当前目录 |
| `/data` | Tape、命令历史、托管插件项目、code mode 临时文件 | `BUB_HOME_HOST`，默认 `~/.bub` |
| `/root/.agents` | 全局 Agent 技能 | `BUB_AGENT_HOME`，默认 `~/.agents` |

Compose 在容器内设置 `BUB_HOME=/data`。`BUB_HOME` 改变 Bub 的运行时数据根目录，**不会移动**默认的 `~/.bub/config.yml`；容器中的配置文件路径仍按容器用户的主目录解析。非敏感设置优先写进 `.env`。

工作区挂载决定模型和工具能看到哪些文件。不要把宿主机根目录或包含密钥的目录整体挂进 `/workspace`。

## 3. 启动 {#start}

使用发布镜像：

```bash
docker compose pull
docker compose up -d
docker compose logs -f app
```

Compose 默认使用 `ghcr.io/bubbuild/bub:latest`。发布工作流还会生成：

- 完整版本 tag，例如 `0.6.0` 或预发布 tag `0.6.0a2`；
- 正式版的 `<major>.<minor>` tag，例如 `0.6`；
- 仅正式版更新 `latest`。

需要可重复部署时，把 `BUB_IMAGE` 固定到完整版本：

```bash
BUB_IMAGE=ghcr.io/bubbuild/bub:0.6.0
```

本地构建：

```bash
docker compose up -d --build
```

本地构建会安装系统工具并执行：

```bash
uv sync --locked --no-dev --no-editable --extra app
```

首次构建通常需要几分钟。构建出的镜像使用 Compose 中的 `BUB_IMAGE` tag；如果该 tag 与远端同名，后续 `docker compose pull` 会重新拉取远端镜像。开发时可以使用自己的 tag，例如 `BUB_IMAGE=bub-local:dev`。

### 不用 Compose {#docker-run}

直接运行镜像时，挂载和启动命令与 Compose 等价：

```bash
docker run -d --name bub --restart unless-stopped \
  --env-file .env \
  -e BUB_HOME=/data \
  -v "$PWD":/workspace \
  -v "$HOME/.bub":/data \
  -v "$HOME/.agents":/root/.agents \
  ghcr.io/bubbuild/bub:latest

docker logs -f bub
```

`docker run` 不会自动读取 Compose 的 `environment` 段，因此这里显式传入 `BUB_HOME=/data`。升级时拉取新 tag，删除旧容器，再用相同卷重新创建；不要在升级前删除 `/data`。

## 4. 启动脚本做什么 {#entrypoint}

容器每次启动时，`entrypoint.sh` 依次执行：

1. 如果 `/workspace/bub-reqs.txt` 存在，把里面的 Python 包装入镜像虚拟环境。
2. 激活 `/app/.venv`，运行无参数 `bub install`，同步 `/data/bub-project` 中的托管插件。
3. 如果 `/workspace/startup.sh` 存在，用 `bash` 执行它；否则执行 `bub gateway`。

因此，`bub install` 添加的插件会在容器重启后继续存在。需要把额外依赖固定在工作区时，可以提交 `bub-reqs.txt`；它适合镜像中无法通过插件项目声明的包，但会延长每次启动时间。

用 `startup.sh` 覆盖默认入口：

```bash
#!/bin/bash
# /workspace/startup.sh
set -euo pipefail
exec /app/.venv/bin/bub gateway --enable-channel telegram
```

脚本必须 `exec` 最终的长期进程，否则容器信号会停在 shell 上。需要自定义渠道组合时，在这里传 `--enable-channel`，或改用 `BUB_ENABLED_CHANNELS`。

## 5. 验证 {#verify}

```bash
docker compose ps
docker compose logs -f app
```

Telegram 正常启动时会记录类似：

```text
telegram.start polling
```

检查变量是否传入而不打印值：

```bash
docker compose exec app sh -c 'test -n "$BUB_TELEGRAM_TOKEN" && echo token-present'
```

如果容器反复重启，先看日志中的插件导入失败或配置校验错误。`bub install` 失败会阻止 `entrypoint.sh` 继续执行，这是为了避免带着半安装的插件启动网关。

## 6. 升级与回滚 {#upgrade}

升级前备份 `/data` 和 `.env`。Tape 是追加写入的 JSONL；备份时应停止写入，或使用文件系统快照：

```bash
docker compose stop app
tar -czf "bub-data-$(date +%Y%m%d-%H%M%S).tar.gz" "$HOME/.bub"
docker compose start app
```

使用发布镜像升级：

```bash
docker compose pull
docker compose up -d
docker compose logs -f app
```

本地构建升级：

```bash
git pull
docker compose build --pull
docker compose up -d
```

回滚到固定版本只需换回旧 tag：

```bash
BUB_IMAGE=ghcr.io/bubbuild/bub:0.6.0 docker compose up -d
```

如果新版本改动了插件依赖或数据格式，同时恢复对应的 `/data` 备份。不要假定旧代码能读取新版本已经写入的全部数据。

### 管理容器内插件 {#plugins}

托管插件项目位于 `/data/bub-project`。以下命令只影响该虚拟环境，不修改系统 Python：

```bash
docker compose exec app bub install
docker compose exec app bub install https://github.com/owner/repo.git@v1.2.0
docker compose exec app bub update
docker compose exec app bub update specific-plugin
```

无参数 `bub install` 按项目声明同步；带参数会新增或锁定插件。`bub update` 升级全部包，也可以指定包名。修改后重启容器，或重新运行启动脚本，让网关加载新入口点。

`bub install` 与 `bub update` 要求 Bub 自身位于虚拟环境中。官方镜像满足这个条件，`entrypoint.sh` 也会先激活 `/app/.venv`。

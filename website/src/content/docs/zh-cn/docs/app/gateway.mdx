Bub 最初的灵感源于 OpenClaw、nanobot 这类常驻型 Agent。因此除了在终端里对话，Bub 也自带了网关（Gateway）模式，可以一直挂在后台响应聊天软件里的消息。

运行 `bub gateway` 即可启动所有已启用的消息渠道。Bub 内置了 Telegram 渠道，其他平台可通过社区[插件](https://hub.bub.build/)接入。

## 启动 Telegram 网关 {#telegram}

:::note
开始前请确认已安装并配置 Bub，且已从 [@BotFather](https://t.me/BotFather) 获取机器人 Token。
:::

<Steps>

1. **配置 `.env`**

   在工作区根目录的 `.env` 中填入 Token 和允许访问的用户 ID（可通过 [@userinfobot](https://t.me/userinfobot) 查询你的数字 ID）：

   ```bash title=".env"
   BUB_TELEGRAM_TOKEN=123456789:your-telegram-bot-token
   BUB_TELEGRAM_ALLOW_USERS=123456789
   ```

2. **启动网关**

   在工作区目录中运行：

   ```bash
   bub gateway
   ```

   启动成功后会输出如下日志：

   ```text
   telegram.start allow_users_count=1 allow_chats_count=0 proxy_enabled=False
   telegram.start polling
   ```

3. **验证私聊**

   试着向机器人发一条私聊消息，稍等片刻看是否收到回复。若无响应，请参考 [回复发送机制](#telegram-outbound) 和 [故障排查](#troubleshooting)。

</Steps>

网关要求至少启用一个渠道。只要 `BUB_TELEGRAM_TOKEN` 非空，Telegram 渠道就会自动启用。

## 配置 Telegram {#configure-telegram}

### 访问白名单 {#restrict-access}

使用 `BUB_TELEGRAM_ALLOW_USERS` 限制可访问的用户，使用 `BUB_TELEGRAM_ALLOW_CHATS` 限制可访问的群组或会话（多个值用逗号分隔，用户名区分大小写）：

```bash
BUB_TELEGRAM_ALLOW_USERS=123456789,your_username
BUB_TELEGRAM_ALLOW_CHATS=-1001234567890,-1009876543210
```

| 白名单配置 | 放行条件 | 未通过时的行为 |
| --- | --- | --- |
| `BUB_TELEGRAM_ALLOW_USERS` | 用户数字 ID 或用户名匹配 | 回复 `Access denied.` |
| `BUB_TELEGRAM_ALLOW_CHATS` | 聊天 ID 匹配 | 静默丢弃消息 |

两项同时配置时，必须同时满足才放行。**两项均为空时，任何用户都能调用你的机器人**——公网部署前请至少配置一项。

### 群聊触发规则 {#telegram-inbound}

将机器人拉入群聊前，需先在 [@BotFather](https://t.me/BotFather) 中关闭 **Privacy Mode**（隐私模式），否则机器人只能收到 `/` 开头的斜杠命令，看不到普通群消息。

为了避免机器人在群里对所有人的闲聊都随便插话，Bub 按以下规则决定是否接收群消息：

| 消息类型 | 触发条件 |
| --- | --- |
| 私聊非命令消息 | 全部接收 |
| 群聊文本消息 | `@<bot_username>`、正文包含 `bub`（不区分大小写，子串匹配，故 `bubble` 也会命中），或直接回复机器人的消息 |
| 群聊带文字说明的图片/文件 | 与群聊文本消息相同 |
| 群聊无文字说明的图片/贴纸/文件 | 仅在直接回复机器人的消息时接收 |
| `/bub <text>` | 去掉 `/bub ` 前缀后作为提示词交给 Bub |

未命中的群消息默认忽略；但如果该群刚触发过机器人、仍处于活跃窗口（`BUB_ACTIVE_TIME_WINDOW`）内，后续跟进消息也会并入当前批次（见[合并连续消息](#merge-consecutive-messages)）。

### 回复发送机制 {#telegram-outbound}

在 Telegram 渠道中，**普通对话消息**和**逗号命令**走不同的回复路径：

| 输入类型 | `output_channel` | 回复方式 |
| --- | --- | --- |
| 普通对话消息 | `"null"`（关闭框架自动直发） | 由模型调用内置的 `telegram` 技能发送回复、引用消息或更新进度 |
| 逗号命令（如 `,help`） | `"telegram"` | 不经过模型，框架直接把工具输出发回原 `chat_id` |

为什么要这样设计？因为在群聊或长任务中，Agent 往往需要先发一条状态提示、中途原地编辑那条消息，或者判断某条群消息根本不需要插话。把普通消息交给内置的 `telegram` 技能，模型就能自主决定何时以及如何回复。

:::note
对于普通消息，**模型必须调用 `telegram` 技能，用户才会在 Telegram 中收到回复**。Turn 运行期间顶部的 `typing...` 状态每 4 秒自动续期一次，仅表示后台仍在运行。
:::

逗号命令（如 `,tape.info`）不经过模型，框架直接发回输出：若返回的是带 `message` 字段的 JSON，则只发送 `message` 内容；其他非空文本原样发送；空输出直接忽略。

### 合并连续消息 {#merge-consecutive-messages}

在即时通讯软件里，大家经常习惯把一句话拆成好几条短消息连着发（比如先发一句「帮我看看这个报错」，紧接着再贴一段日志）。如果每条都立刻触发一次模型调用，不仅浪费 Token，上下文也会支离破碎。因此，Telegram 渠道会自动将短时间内连续到达的消息用换行符拼接，合并为同一个 Turn 处理：

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `BUB_DEBOUNCE_SECONDS` | `1.0` | **活跃消息防抖秒数**：收到私聊或群内直接提及机器人的活跃消息时重置倒计时，等待用户把话说完 |
| `BUB_MAX_WAIT_SECONDS` | `10.0` | **跟进消息最大等待秒数**：收到群内未直接 @ 机器人的跟进消息时，最多等待多久触发合并 |
| `BUB_ACTIVE_TIME_WINDOW` | `60.0` | **群聊活跃窗口秒数**：触发机器人后的多少秒内，同群未 @ 机器人的普通消息也会并入当前批次 |

以命令前缀（默认 `,`）开头的直接命令不参与合并，收到后立即执行。

### 配置代理 {#telegram-reference}

```bash
BUB_TELEGRAM_PROXY=http://127.0.0.1:7890
# 也支持 socks5://<user>:<YOUR_PROXY_PASSWORD>@host:port
```

## 开发自定义渠道 {#custom-channels}

如果没有现成的社区插件可用，也可以自己实现一个渠道：继承 `Channel` 类并实现 `start`、`stop` 和 `send` 方法即可：

```python showLineNumbers collapse={1-6} {8, 30-37}
import asyncio

from bub.channels.base import Channel
from bub.channels.message import ChannelMessage


class MyChannel(Channel):
    name = "myapp"

    def __init__(self, on_receive, token: str) -> None:
        self._on_receive = on_receive
        self._token = token
        self._listener: asyncio.Task | None = None

    @property
    def enabled(self) -> bool:
        return bool(self._token)

    async def start(self, stop_event: asyncio.Event) -> None:
        # start 不能阻塞主事件循环，需放入后台 Task
        self._listener = asyncio.create_task(self._listen(stop_event))

    async def stop(self) -> None:
        if self._listener is not None:
            self._listener.cancel()

    async def _listen(self, stop_event: asyncio.Event) -> None:
        while not stop_event.is_set():
            chat_id, text = await self._next_message()
            await self._on_receive(
                ChannelMessage(
                    session_id=f"myapp:{chat_id}",
                    channel=self.name,
                    chat_id=chat_id,
                    content=text,
                )
            )

    async def send(self, message: ChannelMessage) -> None:
        await self._post(message.chat_id, message.content)
```

实现要点：

- 收到平台消息时调用框架传入的 `on_receive` 回调。
- `session_id` 建议使用 `<channel>:<chat_id>` 格式，防止跨平台会话冲突。
- 缺少必要配置时让 `enabled` 返回 `False`，网关会自动跳过该渠道。
- 需要防抖合并连续短消息时，将 `needs_debounce` 属性设为 `True`。

通过插件的 `provide_channels` Hook 注册该渠道：

```python
import os
from bub import hookimpl


@hookimpl
def provide_channels(message_handler):
    return [MyChannel(on_receive=message_handler, token=os.environ.get("MYAPP_TOKEN", ""))]
```

安装插件后即可通过 `bub gateway --enable-channel myapp` 启动。

## 注册为后台系统服务 {#daemon}

如果你想让 Bub 作为后台服务常驻运行，可以直接运行下面的命令：

```bash
bub gateway --install

# 卸载服务
# bub gateway --uninstall
```

| 操作系统 | 行为 |
| --- | --- |
| Linux | 注册 systemd 用户服务 `bub-gateway.service`；退出 SSH 后仍需保活请执行 `loginctl enable-linger $USER` |
| Windows | 注册当前用户的计划任务，登录时自启、失败自动重启 |
| macOS | 不支持 `--install`；请使用 `launchd`、`tmux` 或 [Docker 部署](/zh-cn/docs/app/deploy/) |

`--install` 会记录当前的 Python 解释器路径、工作区目录和 `--enable-channel` 参数。更换虚拟环境或移动工作区后，请重新运行 `bub gateway --install`。

## 故障排查 {#troubleshooting}

| 现象 | 可能原因 | 解决方法 |
| --- | --- | --- |
| `No channels are enabled` | 未启用任何渠道 | 检查 Token 和 `.env` 路径；运行 `bub hooks` 检查渠道插件 |
| 日志无 `telegram.start` | `BUB_TELEGRAM_TOKEN` 为空 | 检查环境变量是否已传入 `bub` 进程 |
| 私聊收到 `Access denied.` | 用户不在白名单中 | 将用户数字 ID 或用户名加入 `BUB_TELEGRAM_ALLOW_USERS` |
| 私聊无任何响应 | 聊天 ID 不在白名单中 | 将聊天 ID 加入 `BUB_TELEGRAM_ALLOW_CHATS` |
| 群聊无响应 | 未关闭 Privacy Mode 或未触发接收条件 | 在 BotFather 关闭 Privacy Mode；测试时直接 @ 机器人 |
| 一直显示 typing 但无回复 | 模型未调用 `telegram` 技能 | 见[回复发送机制](#telegram-outbound) |
| `409 Conflict` | 同一 Token 启动了多个网关实例 | 停止重复的网关进程 |
| 重启后未处理离线期间的消息 | 启动时默认丢弃积压的历史更新 | 预期行为 |

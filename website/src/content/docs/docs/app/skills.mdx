title: Skills
description: Write, verify, and distribute Bub skills, and understand how skills are discovered and loaded.
---

A skill keeps a set of instructions in `SKILL.md` for the model to use on demand. Project-specific skills can live in the workspace, while general skills can ship with a Python package.

Skill discovery and loading are Bub app behavior. A plain `core.Agent` only uses the prompts you explicitly provide.

## Bundled skills {#builtin-skills}

The Bub installation ships three skills; a skill with the same name in a project or user directory overrides them:

| Skill | Purpose | External dependency |
| --- | --- | --- |
| `telegram` | Send, reply to, and edit Telegram messages | Telegram Bot token |
| `gh` | Manage repositories, issues, PRs, and Actions through the GitHub CLI | `gh` installed and authenticated |
| `skill-creator` | Guide the creation or update of skills | None |

Run `bub run ",skill"` to see the full list actually discovered in the current workspace. Bundled skills are listed too, which does not mean the corresponding external service has been configured.

## Create a project skill {#write-a-skill}

Create `.agents/skills/repo-map/SKILL.md` in the workspace:

```markdown
---
name: repo-map
description: Read the local repository structure before changing code.
---

1. Run `rg --files` to see the repository structure.
2. Read the files that explain this change.
3. Describe the affected modules before editing code.
```

`name` must match the directory name. `description` helps the model decide when to use the skill, so state the task and when it applies.

## Verify a skill {#verify-a-skill}

Run this in the workspace:

```bash
bub run ",skill name=repo-map"
```

The command prints the skill body directly without calling the model. If it returns `(no such skill)`, check the file path, directory name, and YAML frontmatter.

Reference it explicitly in a model session:

```bash
bub run 'Use the $repo-map skill, then list the top-level modules you found.'
```

`$repo-map` expands the skill body into that Turn's system prompt. The model then calls the tools provided by the app to carry out the steps; this example requires `rg` to be installed in the execution environment.

## SKILL.md fields {#skill-fields}

| Field | Requirement |
| --- | --- |
| `name` | Required; matches the directory name; lowercase letters or digits separated by hyphens; at most 64 characters |
| `description` | Required; non-empty string; at most 1,024 characters |
| `metadata` | Optional mapping; keys and values must be strings |

Supporting files can live in directories such as `scripts/`, `references/`, and `assets/`. The skill body supports:

| Variable | Expansion |
| --- | --- |
| `$SKILL_DIR` | Absolute path of the skill directory |
| `$PYTHON` | Path of the Python interpreter running Bub |
| `${config.path.to.value}` | Value of the corresponding field in the Bub configuration |

Scripts in a skill do not run automatically just because the files exist. The model still needs to call them through a tool, so also provide instructions for using the script and the tools it requires.

## Discovery order and loading {#discovery}

By default, the app searches in the following order, and the first match wins when names collide:

1. `<workspace>/.agents/skills/`
2. `~/.agents/skills/`
3. Installed `skills` namespace packages, including Bub's bundled skills

A project skill can therefore override a packaged skill with the same name. The legacy project directory `.agent/skills/` is still read and produces a migration warning; use `.agents/skills/` for new skills.

`BubAgent(skill_dirs=...)` replaces the default search locations with the set of directories you supply, and their order is the priority; pass an empty collection to disable skill discovery.

Every model Step's system prompt lists the names and descriptions of available skills. The body of a skill is expanded for the current Turn only when the prompt contains `$skill-name`. `,skill name=skill-name` is a separate command invocation that only prints the body.

## Distribute with a Python package {#include-skills-in-a-wheel}

Add a `skills` namespace package under `src/`:

```text
src/
├── bub_myplugin/
│   ├── __init__.py
│   └── plugin.py
└── skills/
    └── my-skill/
        ├── SKILL.md
        └── references/
            └── examples.md
```

With Hatch, include both directories in the wheel:

```toml
[tool.hatch.build.targets.wheel]
packages = ["src/bub_myplugin", "src/skills"]
```

Do not add an `__init__.py` inside `skills/`. Namespace packages let multiple distributions contribute skills together; other build tools should also produce the same installed directory layout.

Skills can ship with a plugin or be packaged independently; they are not required to implement hooks at the same time.

## Check the installation {#verify-installation}

Install the built wheel into the same environment that runs Bub, then run:

```bash
bub run ",skill name=my-skill"
```

If the skill cannot be found, check whether the wheel contains `skills/my-skill/SKILL.md`. If another version is printed, check whether a project or user directory has a skill with the same name, since those have higher priority.

For general wheel building, CLI packaging, and complete release verification, see [Embedding and distribution](/docs/app/distribution/).

title: Plugins

Plugins change Bub app behavior through hooks. A Python package declares a plugin object in the `bub` entry point group; Bub imports it and wires its hook implementations into the app.

The following first builds an echo plugin that needs no model credentials, so you can verify the complete create, install, and run flow. To reuse existing plugins, see [Reuse the Bub app](/docs/sdk/reuse-app/).

## Create a plugin {#create-a-plugin}

Prepare Python 3.12+ and [uv](/docs/getting-started/install/), then create this project:

```text
bub-echo-plugin/
├── pyproject.toml
└── src/
    └── bub_echo_plugin/
        ├── __init__.py
        └── plugin.py
```

`src/bub_echo_plugin/__init__.py` can stay empty. Declare the package and entry point in `pyproject.toml`:

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "bub-echo-plugin"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["bub[app]"]

[project.entry-points."bub"]
echo = "bub_echo_plugin.plugin:echo_plugin"

[tool.hatch.build.targets.wheel]
packages = ["src/bub_echo_plugin"]
```

The entry point key `echo` is the plugin name; the value points to the object to load. Implement the model stage in `src/bub_echo_plugin/plugin.py`:

```python
from bub import hookimpl


class EchoPlugin:
    @hookimpl
    def run_model(self, prompt, session_id, state):
        return f"[echo:{session_id}] {prompt}"


echo_plugin = EchoPlugin()
```

`run_model` replaces the built-in model stage and returns plain text; message preparation, state saving, and reply delivery are still handled by other hooks.

## Install and run {#install-and-run}

Sync the environment in the plugin project, then check the hook report:

```bash
uv sync
uv run bub hooks
```

`uv sync` installs the current project in editable mode. `bub hooks` should list `echo` under `run_model`, while the built-in Agent appears under `run_model_stream`.

```bash
uv run bub run "hello from my plugin"
```

When no other higher-priority model implementation exists, the output contains:

```text
[echo:cli:local] hello from my plugin
```

If `echo` does not appear, check in order:

1. Whether the environment the plugin is installed into is the same one running `bub`;
2. Whether the group name and module path in `[project.entry-points."bub"]` are correct;
3. Whether startup logs recorded a plugin import failure.

Reinstall after changing entry point metadata. If `echo` appears but replies come from elsewhere, check other model hooks and their [priority](/docs/reference/hooks/#priority-and-dispatch).

Bub registers built-in implementations first, then entry point plugins. At equal priority, implementations registered later run first; `tryfirst` and `trylast` can adjust the order.

## Choose an entry point form {#entry-point-forms}

| Entry point target | Behavior | Use it when |
| --- | --- | --- |
| `bub_myplugin.plugin` | Registers the module | Hooks are module-level functions |
| `bub_myplugin.plugin:plugin` | Registers an existing instance | Hooks share object state |
| `bub_myplugin.plugin:MyPlugin` | Calls the class or factory and registers the return value | Hooks need access to `BubFramework` |

When the entry point value is callable, Bub passes the current `BubFramework` to it:

```python
from bub import BubFramework, hookimpl


class MyPlugin:
    def __init__(self, framework: BubFramework) -> None:
        self.framework = framework

    @hookimpl
    def build_prompt(self, message, session_id, state):
        return f"Describe the workspace at {self.framework.workspace}."
```

`build_prompt` replaces the model input. A real extension should choose the hook that matches its responsibility; see [Application hooks](/docs/app/hooks/).

## Provide tools {#provide-tools}

New plugins should explicitly provide `@tool` objects through `provide_tools`:

```python
from bub import hookimpl, tool
from bub.core.tools import Tool


@tool(name="orders.get")
def get_order(order_id: str) -> dict[str, str]:
    """Look up an order by id."""
    return {"id": order_id, "status": "shipped"}


class OrdersPlugin:
    @hookimpl
    def provide_tools(self) -> list[Tool]:
        return [get_order]
```

`BubAgent` takes a snapshot of the current tools when constructed. To add tools during a run, update that instance's `tools` dictionary; new Agents collect the tools again.

Legacy plugins that rely on automatic `@tool` collection when their entry point loads, and do not implement `provide_tools`, still register their tools and produce a deprecation warning. New plugins should not use this fallback. See [Tools](/docs/app/tools/) for tool parameters, deferred loading, and code mode.

## Provide long-running services {#lifecycle}

Components such as MCP clients and schedulers need to start with the process rather than in response to a message. Implement `Lifecycle` and provide it through `provide_channels` like any other channel:

```python
from bub.channels.base import Lifecycle


class MyRuntime(Lifecycle):
    name = "myapp.lifecycle"

    async def start(self, stop_event) -> None:
        await self._connect(stop_event)

    async def stop(self) -> None:
        await self._close()
```

Lifecycle channels start and stop with the channel runtime and do not receive messages:

- They appear among the channel names accepted by `--enable-channel`;
- When ordinary channels are listed explicitly, enabled `Lifecycle` channels are still attached automatically;
- Exclude one with `!name`, for example `--enable-channel '!mcp.lifecycle'`;
- `bub run` does not start channels, so it also does not start long-running services.

For complete examples, see [`bub-mcp`](https://github.com/bubbuild/bub-contrib/tree/main/packages/bub-mcp) and [`bub-schedule`](https://github.com/bubbuild/bub-contrib/tree/main/packages/bub-schedule).

## Share a plugin {#share-a-plugin}

A single distribution can provide a plugin, channels, and [skills](/docs/app/skills/#include-skills-in-a-wheel) at the same time:

```toml
[project.entry-points."bub"]
orders = "bub_orders.plugin"

[tool.hatch.build.targets.wheel]
packages = ["src/bub_orders", "src/skills"]
```

For general wheel building, CLI packaging, and pre-release verification, see [Packaging and distribution](/docs/app/distribution/). Agent Plugins instead use `plugin.json`, skills, and MCP server definitions; see [Load Agent Plugins](/docs/integrations/agent-plugins/).

## WASM plugins (experimental) {#wasm-plugins}

[`bub-extism`](https://github.com/bubbuild/bub-contrib/tree/main/packages/bub-extism) exposes WebAssembly module export functions as hooks through Extism, so plugins can also be written in other languages:

```bash
bub install bub-extism@main
bub hooks
```

`extism.json` specifies the module files and hook mapping:

```json
{
  "plugins": {
    "prompt": {
      "manifest": { "wasm": [{ "path": "go-build-prompt.wasm" }] },
      "wasi": true,
      "hooks": { "build_prompt": "build_prompt" }
    }
  }
}
```

```bash
export BUB_EXTISM_CONFIG_PATH=./extism.json
bub run "Say hello from a prompt built outside Python."
```

Not every hook supports WASM, and arguments must cross the Python-to-WASM boundary. Before using it, check the [plugin README](https://github.com/bubbuild/bub-contrib/tree/main/packages/bub-extism) for the supported list and examples.

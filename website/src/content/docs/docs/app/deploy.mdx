---
title: Deployment
description: Run the Bub gateway with Docker Compose, persist its data, and upgrade safely.
---

Bub can run as a long-lived container. The official image includes the runtime, common command-line tools, and the managed plugin environment; the host only needs to provide `.env`, a workspace, and a data directory.

There are two ways to get started:

- **Use a release image**: download [`docker-compose.yml`](https://github.com/bubbuild/bub/blob/main/docker-compose.yml) and [`env.example`](https://github.com/bubbuild/bub/blob/main/env.example) from the repository. No source code is needed.
- **Build locally**: get a source archive from [GitHub Releases](https://github.com/bubbuild/bub/releases), or clone the repository, then build with the same Compose file.

The image is defined by [`Dockerfile`](https://github.com/bubbuild/bub/blob/main/Dockerfile) and [`entrypoint.sh`](https://github.com/bubbuild/bub/blob/main/entrypoint.sh) in the repository.

## Before you start {#before-you-start}

- Install Docker and Compose v2, and confirm that `docker compose version` works.
- Prepare the model configuration. `.env` must contain at least `BUB_MODEL`, plus either `BUB_API_KEY` or a provider-specific key. See [Configure](/docs/app/configure/) for the fields.
- To run the Telegram gateway, prepare `BUB_TELEGRAM_TOKEN` and a user or group allowlist. See [Telegram gateway](/docs/app/gateway/#telegram).

The container runs as `root`. If a host directory was created by another user, first confirm that the Docker process can read and write that path.

## 1. Prepare the configuration {#configure}

Create `.env` in the directory that contains the Compose file:

```bash
cp env.example .env
```

A minimal Telegram configuration:

```bash
BUB_MODEL=openrouter:openrouter/free
BUB_API_KEY=sk-or-...
BUB_TELEGRAM_TOKEN=123456:abcdef...
BUB_TELEGRAM_ALLOW_USERS=123456789
```

In production, set `BUB_TELEGRAM_ALLOW_CHATS` or `BUB_TELEGRAM_ALLOW_USERS` as well. Leaving the allowlist blank lets anyone who finds the bot start a session.

`docker compose` reads `.env` and passes it to the container. Do not commit an `.env` that contains tokens.

## 2. Understand the mounts {#volumes}

By default, the Compose file uses three bind mounts:

```yaml
volumes:
  - ${BUB_WORKSPACE_PATH:-.}:/workspace
  - ${BUB_HOME_HOST:-${HOME}/.bub}:/data
  - ${BUB_AGENT_HOME:-${HOME}/.agents}:/root/.agents
```

| Container path | Contents | Host variable |
| --- | --- | --- |
| `/workspace` | The working directory for Bub's tools | `BUB_WORKSPACE_PATH`, default current directory |
| `/data` | Tape, command history, managed plugin project, code mode temporary files | `BUB_HOME_HOST`, default `~/.bub` |
| `/root/.agents` | Global Agent skills | `BUB_AGENT_HOME`, default `~/.agents` |

Compose sets `BUB_HOME=/data` inside the container. `BUB_HOME` changes the root of Bub's runtime data; it **does not move** the default `~/.bub/config.yml`. The configuration file path in the container is still resolved from the container user's home directory. Prefer writing non-sensitive settings to `.env`.

The workspace mount determines which files the model and tools can see. Do not mount the host root, or any directory that contains secrets, as `/workspace`.

## 3. Start {#start}

With a release image:

```bash
docker compose pull
docker compose up -d
docker compose logs -f app
```

Compose uses `ghcr.io/bubbuild/bub:latest` by default. The release workflow also produces:

- a full version tag, such as `0.6.0`, or a prerelease tag such as `0.6.0a2`;
- a `<major>.<minor>` tag for stable releases, such as `0.6`;
- updates to `latest` only for stable releases.

For reproducible deployments, pin `BUB_IMAGE` to a full version:

```bash
BUB_IMAGE=ghcr.io/bubbuild/bub:0.6.0
```

To build locally:

```bash
docker compose up -d --build
```

A local build installs system tools and runs:

```bash
uv sync --locked --no-dev --no-editable --extra app
```

The first build usually takes a few minutes. The built image uses the `BUB_IMAGE` tag from the Compose file; if that tag matches a remote tag of the same name, a later `docker compose pull` pulls the remote image again. During development you can use your own tag, for example `BUB_IMAGE=bub-local:dev`.

### Without Compose {#docker-run}

Running the image directly uses the same mounts and start command as Compose:

```bash
docker run -d --name bub --restart unless-stopped \
  --env-file .env \
  -e BUB_HOME=/data \
  -v "$PWD":/workspace \
  -v "$HOME/.bub":/data \
  -v "$HOME/.agents":/root/.agents \
  ghcr.io/bubbuild/bub:latest

docker logs -f bub
```

`docker run` does not read the Compose `environment` section automatically, so `BUB_HOME=/data` is passed explicitly here. To upgrade, pull the new tag, remove the old container, and recreate it with the same volumes; do not delete `/data` before upgrading.

## 4. What the startup script does {#entrypoint}

On every container start, `entrypoint.sh` does the following in order:

1. If `/workspace/bub-reqs.txt` exists, install the Python packages listed in it into the image's virtual environment.
2. Activate `/app/.venv` and run `bub install` with no arguments, which syncs the managed plugins in `/data/bub-project`.
3. If `/workspace/startup.sh` exists, run it with `bash`; otherwise run `bub gateway`.

As a result, plugins added by `bub install` survive container restarts. To pin extra dependencies in the workspace, commit `bub-reqs.txt`; it suits packages in the image that cannot be declared through a plugin project, but it lengthens every startup.

Use `startup.sh` to override the default entrypoint:

```bash
#!/bin/bash
# /workspace/startup.sh
set -euo pipefail
exec /app/.venv/bin/bub gateway --enable-channel telegram
```

The script must `exec` the final long-lived process; otherwise container signals stop at the shell. To customize the channel combination, pass `--enable-channel` here, or use `BUB_ENABLED_CHANNELS`.

## 5. Verify {#verify}

```bash
docker compose ps
docker compose logs -f app
```

A healthy Telegram start logs something like:

```text
telegram.start polling
```

Check that a variable was passed in without printing its value:

```bash
docker compose exec app sh -c 'test -n "$BUB_TELEGRAM_TOKEN" && echo token-present'
```

If the container keeps restarting, first look for plugin import failures or configuration validation errors in the logs. A failed `bub install` stops `entrypoint.sh` from continuing, which avoids starting the gateway with half-installed plugins.

## 6. Upgrade and roll back {#upgrade}

Before upgrading, back up `/data` and `.env`. Tape is append-only JSONL; stop writes during the backup, or use a filesystem snapshot:

```bash
docker compose stop app
tar -czf "bub-data-$(date +%Y%m%d-%H%M%S).tar.gz" "$HOME/.bub"
docker compose start app
```

To upgrade with a release image:

```bash
docker compose pull
docker compose up -d
docker compose logs -f app
```

To upgrade a local build:

```bash
git pull
docker compose build --pull
docker compose up -d
```

To roll back to a pinned version, switch back to the old tag:

```bash
BUB_IMAGE=ghcr.io/bubbuild/bub:0.6.0 docker compose up -d
```

If the new version changed plugin dependencies or the data format, restore the matching `/data` backup as well. Do not assume that the old code can read all the data the new version has written.

### Manage plugins inside the container {#plugins}

The managed plugin project lives at `/data/bub-project`. The following commands affect only that virtual environment and do not modify the system Python:

```bash
docker compose exec app bub install
docker compose exec app bub install https://github.com/owner/repo.git@v1.2.0
docker compose exec app bub update
docker compose exec app bub update specific-plugin
```

`bub install` with no arguments syncs according to the project declarations; with arguments it adds or pins a plugin. `bub update` upgrades all packages, or a named package. After changing plugins, restart the container, or rerun the startup script, so the gateway loads the new entry points.

`bub install` and `bub update` require Bub itself to live in a virtual environment. The official image satisfies this, and `entrypoint.sh` activates `/app/.venv` first.

---
title: Connect a local llama.cpp model
description: Start a local llama.cpp server and have Bub call GGUF models through an OpenAI-compatible endpoint.
---

This guide uses `llama.cpp` to serve an OpenAI-compatible API on your machine, then points the Bub application's model requests at that endpoint.

The model itself, inference speed, and memory usage are still determined by `llama.cpp`; Bub's turn, tool, and Tape behavior is unchanged.

The example model is the Q8 quantized version of [`ggml-org/gemma-4-E2B-it-GGUF`](https://huggingface.co/ggml-org/gemma-4-E2B-it-GGUF). You can substitute any GGUF model that `llama.cpp` can load, as long as you update the file names and model alias accordingly.

## Before you begin {#before-you-start}

- You have [installed the Bub application](/docs/getting-started/install/#app-install).
- Docker is installed and `docker version` can connect to the daemon.
- You have at least 8 GB of available memory; the Q8 model file is about 5 GB, and you still need room for context and batching at runtime.
- You have downloaded the quantized files from the **Files** tab of the Hugging Face model page to `~/.cache/llama.cpp/`. This guide uses:

```text
~/.cache/llama.cpp/ggml-org_gemma-4-E2B-it-GGUF_gemma-4-E2B-it-Q8_0.gguf
~/.cache/llama.cpp/ggml-org_gemma-4-E2B-it-GGUF_mmproj-gemma-4-E2B-it-Q8_0.gguf
```

Use whatever file names the repository actually contains. `mmproj` is the multimodal projection needed for image input; you can omit it when only handling text.

## 1. Start llama-server {#start-server}

First set an API key used only for local connections:

```bash
export LLAMA_API_KEY="local-$(openssl rand -hex 8)"
echo "$LLAMA_API_KEY"
```

Start the container:

```bash
docker run --rm -it \
  -p 127.0.0.1:8080:8080 \
  -v "$HOME/.cache/llama.cpp:/models:ro" \
  ghcr.io/ggml-org/llama.cpp:server \
  --host 0.0.0.0 \
  --port 8080 \
  --api-key "$LLAMA_API_KEY" \
  --alias gemma-4-E2B-it \
  -m /models/ggml-org_gemma-4-E2B-it-GGUF_gemma-4-E2B-it-Q8_0.gguf \
  --mmproj /models/ggml-org_gemma-4-E2B-it-GGUF_mmproj-gemma-4-E2B-it-Q8_0.gguf
```

Notes:

- `-p 127.0.0.1:8080:8080` listens only on the host loopback address, so other machines cannot reach it directly.
- `--alias` is the model name used in `/v1/chat/completions`.
- `/models` inside the container maps to the read-only model cache on the host.
- Under SELinux enforcing mode, if the container cannot read the mounted files, add `--security-opt label=disable` to `docker run`.
- Without an available GPU, `llama.cpp` falls back to CPU; device or backend warnings may appear in the logs, but the service is still usable for verifying the integration.
- Wait for `server is listening on` in the logs before continuing. The first load of a large model can take tens of seconds.

Explicitly exposing the server on `0.0.0.0` changes the security boundary. Do not expose an inference endpoint to the public internet without authentication and a firewall.

## 2. Verify the OpenAI-compatible endpoint {#verify-endpoint}

In the same shell, request the model list:

```bash
curl -sS http://127.0.0.1:8080/v1/models \
  -H "Authorization: Bearer $LLAMA_API_KEY"
```

Then send a chat request:

```bash
curl -sS http://127.0.0.1:8080/v1/chat/completions \
  -H "Authorization: Bearer $LLAMA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gemma-4-E2B-it",
    "messages": [{"role": "user", "content": "Reply with one word: hello"}],
    "max_tokens": 16
  }'
```

A successful request returns `chat.completion` JSON containing `choices[0].message.content`. If you get `401`, check that curl and the container use the same `LLAMA_API_KEY`; if you get a model-not-found error, check `--alias`.

`LLAMA_API_KEY` exists only in the shell that started it. A new terminal must export the same value again, or you can write a test value directly in the command.

## 3. Configure Bub {#configure-bub}

In the same shell, set the model endpoint and credentials:

```bash
export BUB_OPENAI_API_BASE="http://127.0.0.1:8080/v1"
export BUB_OPENAI_API_KEY="$LLAMA_API_KEY"
export BUB_MODEL="openai:gemma-4-E2B-it"
```

`BUB_OPENAI_*` only affects the `openai` provider. If every provider should use the same compatible endpoint, you can also use the generic `BUB_API_BASE` and `BUB_API_KEY`; provider-specific variables take precedence.

Run a turn:

```bash
bub run "Reply with one short sentence: hello from a local model."
```

The output should start with `[cli:local]` and contain the model's reply. The request path is:

```text
Bub turn -> openai provider -> http://127.0.0.1:8080/v1 -> llama.cpp
```

Whether tool calls work depends on the model's instruction-following ability, not on the endpoint type. Verify the connection with a simple question first, then test tools and longer contexts.

## 4. Tune performance and context {#tune}

Adjust the startup parameters to your hardware:

| Goal | Parameter or approach |
| --- | --- |
| Reduce memory | Use a smaller quantization file, such as Q4_K_M |
| Increase context | Set `--ctx-size`; this increases KV cache memory |
| Use a GPU | Add GPU devices and offload layers according to the `llama.cpp` image documentation |
| Limit concurrency | Set `--parallel` and account for the context budget of each slot |
| Text only | Remove `--mmproj` and the corresponding model file |

Restart the container after changing parameters, then re-verify with `/v1/models` and one `bub run`.

:::caution
Do not increase `--ctx-size` without accounting for memory usage. KV cache memory grows with context length, so leave enough physical memory to avoid OOM. Tool definitions and the Tape also consume tokens, so keep the model's context window within what Bub actually needs.
:::

## Cleanup {#cleanup}

Press `Ctrl-C` in the terminal running the container. Then clear Bub's local overrides:

```bash
unset BUB_API_BASE BUB_API_KEY BUB_OPENAI_API_BASE BUB_OPENAI_API_KEY BUB_MODEL LLAMA_API_KEY
```

Tapes and session history remain in Bub's data directory. Switching to another model does not delete them.

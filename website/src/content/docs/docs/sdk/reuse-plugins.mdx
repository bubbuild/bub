---
title: Reusing plugins
description: Bring plugin tools and hooks into your own agent while keeping your existing service and calling code.
---

Use Bub's application plugins in your existing Python service. Your host keeps its HTTP routes, task handlers, and output handling. Choose the agent and runtime according to the application behavior you want to reuse.

`BubAgent` is Bub's existing combination of the core loop, settings, plugin hooks, skills, and tool policies. Its [direct stream entry point](#reuse-bubagent) also works inside a host application. Use `BubFramework.process_inbound()` when you want the full message pipeline.

With `core.Agent`, you choose the components and connect the hooks yourself. The examples below take a search tool from one plugin and adapt the call hooks of another. Each example covers that plugin's dependencies; background services need their own startup and shutdown.

## Add a search tool {#add-a-search-tool}

[`bub-web-search`](https://github.com/bubbuild/bub-contrib/tree/dev/packages/bub-web-search) exposes a search tool that works with `core.Agent`. Install it in the environment that runs your service. These examples use plugin packages from the `dev` branch of `bub-contrib`:

```bash
uv add "bub[app]" \
  "bub-web-search @ git+https://github.com/bubbuild/bub-contrib.git@dev#subdirectory=packages/bub-web-search"
```

The plugin uses application configuration code, so it needs the `app` dependencies. Your program can continue using `core.Agent` with its own model, tape names, and run lifecycle.

For Jina search, set `BUB_SEARCH_PROVIDER=jina` and `BUB_SEARCH_JINA_API_KEY` before starting the process. Set `REPUBLIC_OPENAI_API_KEY` for the model in this example. Save this as `search_agent.py`:

```python
import asyncio
from pathlib import Path

import republic
from bub_web_search.tools import register_tools

from bub.core import Agent
from bub.core.store import FileTapeStore


async def main() -> None:
    search = register_tools()
    if search is None:
        raise RuntimeError("Configure a search provider with BUB_SEARCH_* first.")

    agent = Agent(
        store=FileTapeStore(Path("sessions")),
        tools=[search],
        system_prompt="Search for sources before answering. Include their URLs.",
    )
    async with republic.get_model("openai:gpt-5-mini") as model:
        async with agent.run(
            "Find the official Python asyncio documentation.",
            model=model,
            tape="research-42",
            options={"max_tokens": 4096},
        ) as stream:
            async for event in stream:
                if event.kind == "text":
                    print(event.data.get("delta", ""), end="", flush=True)
                elif event.kind == "error":
                    raise RuntimeError(str(event.data.get("message", "Agent failed")))
        print()


if __name__ == "__main__":
    asyncio.run(main())
```

Run `uv run python search_agent.py`. The plugin handles the search request and its HTTP connection. The Agent records the conversation under `sessions/`, and your code consumes the reply.

For an existing Agent, add the returned tool with `agent.tools[search.name] = search` during startup. Its name is `web.search`; the model sees `web_search`. You can keep the rest of your calling code, including a [FastAPI endpoint](/docs/sdk/web-service/).

`register_tools()` also updates the process-wide tool registry, so do this setup during startup. An Agent uses the tools you explicitly pass or add to it. This example takes the returned search tool; add the package's other tools, such as Jina's `web.read`, separately if needed.

## Extend the run {#extend-the-run}

`AgentPlugins` connects a plugin's hooks to your Agent's events.

### Model and tool calls {#model-and-tool-calls}

[`bub-context-budget`](https://github.com/bubbuild/bub-contrib/tree/dev/packages/bub-context-budget) runs before and after model calls. When its estimate crosses a threshold, it adds an instruction asking the model to call `tape.handoff`. Give the Agent that tool and subscribe the plugin's hooks to its events.

```bash
uv add "bub-context-budget @ git+https://github.com/bubbuild/bub-contrib.git@dev#subdirectory=packages/bub-context-budget"
```

Add this function to your program, then call `add_context_budget(agent)` after creating the Agent and before its first run:

```python
from pathlib import Path

from bub_context_budget import plugin as context_budget

from bub import BubFramework
from bub.builtin.tools import tape_handoff
from bub.core import Agent
from bub.hooks.agent import AgentPlugins


def add_context_budget(agent: Agent) -> None:
    framework = BubFramework(config_file=Path("bub.yml"))
    AgentPlugins(framework, plugins=[context_budget]).attach(agent)
    agent.tools[tape_handoff.name] = tape_handoff
```

The adapter connects this plugin's `before_llm_call` and `after_llm_call` hooks to your Agent. Your model, prompt sections, store, and `agent.run()` stay in place. This example supplies the hooks and handoff tool that context-budget needs. Check those requirements separately when adapting another plugin.

Set the context limit with `BUB_CONTEXT_BUDGET_MAX_CONTEXT_TOKENS` or `context-budget.max_context_tokens` in `bub.yml`. The plugin reserves 16,384 tokens from that limit before requesting a handoff. The budget is advisory: execution depends on the model following the instruction.

A handoff saves its summary on the anchor. To carry that summary into the next model request, include it through your [context selection](/docs/concepts/tape/#context) or next prompt.

Register and attach once during service startup. This plugin runs entirely through call hooks. Registration belongs to the Framework, and `attach()` connects its agent-loop hooks to the selected Agent's events. Every session using that Agent shares those hooks. Separate Framework instances are needed for different plugin sets; configuration remains process-wide.

The adapter catches ordinary plugin exceptions and skips the failed hook. A hook that blocks a tool must return `ToolCallDecision.deny(...)`; see [Agent events](/docs/concepts/events/) for interception semantics.

### Other hooks {#other-hooks}

The other hooks decide what the run has. Each hook maps to a core Agent extension point:

| Hook | Core Agent extension point |
| --- | --- |
| `before_llm_call`, `after_llm_call`, `before_tool_call`, `after_tool_call` | Call events, through `attach(agent)`. |
| `continue_prompt` | `StepFinished` with `status == "continue"`: the hook's text becomes the next step's user message. |
| `provide_steering_inbox` | `MessagesPending` drains the inbox before each model request and when a step ends; drained messages continue the run. |
| `system_prompt` | A prompt section that `attach(agent)` adds after the agent's sections. |
| `provide_tools` | Tools that `attach(agent)` adds; a tool the agent already has by that name is kept. |
| `provide_tape_store`, `build_tape_context`, `provide_tape_sidecar` | `store`, `context` and `sidecars` from `plugins.components()`. |
| `load_state`, `provide_environment` | The run's state from `await plugins.build_state(session_id)`. |

```python
from bub.hooks.agent import AgentPlugins

plugins = AgentPlugins(plugins=[SupportPlugin()])

async with plugins.running():
    agent = plugins.attach(Agent(system_prompt="Answer in plain text.", **plugins.components()))
    state = await plugins.build_state("customer-42", agent=agent)
    async with agent.run(prompt, model=model, tape="customer-42", state=state) as stream:
        ...
```

`components()` leaves out what no hook provides, so the Agent keeps its defaults; arguments you pass yourself take their place. A hook-provided store and steering inbox exist only inside `plugins.running()`, which enters `framework.running()`. Attach before registering your own handlers so they see the hooks' changes.

Message-pipeline hooks, such as `build_prompt`, `run_model`, `save_state`, `render_outbound`, and `dispatch_outbound`, are not part of the agent loop and only run in `process_inbound()`. `plugins=[...]` registers exactly the listed plugins. When several plugins implement the same hook, all of them run: duplicate tools, stores, and tape contexts keep the highest-priority provider, and prompt sections join from low to high priority. `AgentPlugins()` without arguments loads Bub's builtin hooks and the installed plugins, as the `bub` command does; the builtin system prompt asks the agent to reply through channels. Pass `framework` to use an existing framework's hooks; `plugins` given with it are registered on it.

## Choose how to connect {#choose-how-to-connect}

The plugin's implementation determines what your host must provide:

| Plugin capability | How to reuse it |
| --- | --- |
| Tools or a store | Import the public component and pass it to Agent. For example, `bub_tapestore_sqlalchemy.store.SQLAlchemyTapeStore` accepts a database URL and can be passed as `store=`. |
| Model or tool interception, system prompt, continuation, or steering | Register the selected plugin and [attach `AgentPlugins`](#other-hooks). Check any state fields or tools the plugin expects. |
| Message preparation, model-stage replacement, state saving, or delivery | [Embed the application pipeline](/docs/app/distribution/#embed-the-application) in your host. It runs these stages and returns a `TurnResult`. |
| Background connections or discovered tools | Open the service, wait until it is ready, attach its tools, then close it with the host. Follow the plugin's own lifecycle API. |

Follow the chosen store's lifecycle contract. `framework.running()` acquires hook-provided resources and closes the context managers it entered. A store returned as an ordinary object keeps its own cleanup requirements.

For MCP, follow the plugin's [embedding example](https://github.com/bubbuild/bub-contrib/tree/dev/packages/bub-mcp#embedding): connect with `MCPChannel.connect()`, attach tools to a `BubAgent` with `bind_agent()`, and close connections with `stop()`. Your host must manage this lifecycle in addition to `framework.running()`.

## Reuse BubAgent {#reuse-bubagent}

`BubAgent` combines the core loop with Bub settings, skills, tool policies, and plugin hooks. A host can load installed plugins with `framework.load_hooks()`, enter `framework.running()`, then construct `BubAgent(framework)`. Its `run_stream(*, session_id, prompt, state=None, ...)` returns a stream for the host to consume and close.

Choose this when you also want those application defaults. The builtin system prompt asks the agent to send replies through channels. A service that returns model text directly needs its own prompt policy. Replacing `agent.system_prompt` replaces all its sections, including plugin, skills, deferred-tool, and CodeMode instructions.

`run_stream()` uses system-prompt and continuation hooks, call interception, and the configured tape components. With `state` omitted, it loads state using a message containing only the Agent reference. For plugins that need request metadata, prepare state with `framework.build_state(message, session_id)` and pass it to `run_stream(state=...)`. Include the Agent in `message["_runtime_agent"]` so state recovery uses its store.

The direct stream call bypasses the initial `build_prompt`, `run_model` / `run_model_stream`, `save_state`, rendering, and dispatch hooks. The host handles output, saves its own state, and coordinates concurrent runs on one session. Use `process_inbound()` when you need the complete message pipeline; even with `stream_output=True`, that method consumes the stream and returns a completed `TurnResult`.

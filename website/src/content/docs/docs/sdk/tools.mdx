Tools let the model query facts or perform actions. `@tool` converts a typed Python function into a `Tool`: its name, type annotations, and docstring together form the contract visible to the model.

This chapter adds `get_order` to the order assistant. The goal is not merely to invoke a function, but to define what the model sees, how failures come back, and who owns side effects.

## Complete order-query example {#complete-example}

Replace `main.py` with:

```python
import asyncio

import republic

from bub.core import Agent
from bub.core.tools import tool


ORDERS = {
    "A123": {
        "order_id": "A123",
        "status": "shipped",
        "item": "Mechanical keyboard",
        "amount": 399.0,
    }
}


@tool
async def get_order(order_id: str) -> dict[str, str | float]:
    """Look up an order's status, item, and amount. Return error when it does not exist."""
    await asyncio.sleep(0.1)  # Simulate non-blocking database I/O
    if order := ORDERS.get(order_id):
        return order
    return {"order_id": order_id, "error": "order_not_found"}


async def main() -> None:
    agent = Agent(
        tools=[get_order],
        system_prompt="You are an order support assistant. Always use the tool for order lookups; never guess order status.",
        max_steps=6,
        max_tool_concurrency=2,
    )

    async with republic.get_model("openai:gpt-5-mini") as model:
        async with agent.run(
            "What is the current status of order A123?",
            model=model,
            tape="customer-42",
        ) as stream:
            async for event in stream:
                if event.kind == "tool_call":
                    for call in event.data["tool_calls"]:
                        print(f"\n[Tool requested] {call['name']} {call['arguments']}")
                elif event.kind == "tool_result":
                    print(f"[Tool results] {event.data['tool_results']}")
                elif event.kind == "text":
                    print(event.data["delta"], end="", flush=True)
        print()


if __name__ == "__main__":
    asyncio.run(main())
```

Using the `REPUBLIC_OPENAI_API_KEY` from the previous chapter, run:

```bash
uv run python main.py
```

A typical run has two Steps:

1. The model requests `get_order(order_id="A123")`; Bub executes it and yields `tool_result`.
2. The next Step gives that result to the model, which answers from the returned data.

The model still decides whether to call a tool. System prompts guide behavior, but order status must come from tool results; a prompt is not a data-correctness guarantee.

## Design an argument contract the model can use {#schemas}

### Types and descriptions are model-facing API

Parameter types become JSON Schema and the docstring becomes the tool description. Explain business meaning and constraints instead of repeating parameter names:

```python
@tool
async def get_order(order_id: str) -> dict[str, str | float]:
    """Look up an order. order_id is the complete customer-provided ID, such as A123."""
    ...
```

For larger inputs or additional validation, use a Pydantic model:

```python
from pydantic import BaseModel, Field

from bub.core.tools import tool


class RefundInput(BaseModel):
    order_id: str = Field(description="Complete order ID, such as A123")
    amount: float = Field(gt=0, description="Refund amount; must be greater than zero")
    reason: str = Field(min_length=1, description="Customer-provided refund reason")


@tool(name="refund_order", model=RefundInput)
def refund_order(param: RefundInput) -> dict[str, str | float]:
    """Request a refund for a paid order; authorization must run before execution."""
    return {
        "order_id": param.order_id,
        "amount": param.amount,
        "status": "refund_requested",
    }
```

Validation failures become tool errors in `tool_result`, so the model can correct its arguments and retry, although a successful retry is not guaranteed. Domain states such as “order not found” can use stable structured error objects so the model and caller can distinguish them.

## Results, exceptions, and side effects {#results-and-errors}

Ordinary return values pass through `Tool.render()` to become model-facing text: strings stay unchanged, while Pydantic models, dictionaries, and other structured values are serialized as JSON by default. Pass a `renderer` to control that representation. Never include credentials or host-only internal fields in a tool result.

| Situation | Default behavior |
| --- | --- |
| Arguments fail types or Pydantic constraints | Converted to a validation tool error returned to the model |
| Tool raises an ordinary exception | Converted to a tool error returned to the model |
| Tool returns a domain error object | Returned to the model as a normal tool result |
| Storage, model, or event handler aborts the Run | Exception may propagate from stream iteration to the host |

**Tool side effects are outside the Tape transaction boundary.** A refund, sent email, or changed file is not rolled back by a later model failure, client cancellation, or `merge_back=False`. Writes need authorization, idempotency keys, and business compensation where necessary; do not rely on a prompt asking the model not to repeat a call.

### Return images and other media {#media-results}

Use `content_result()` to return media to the current model call instead of embedding binary data in JSON:

```python
import republic

from bub.core.tools import content_result, tool


@tool
def get_invoice_preview(invoice_id: str) -> dict[str, object]:
    """Return an invoice description and preview image."""
    return content_result([
        f"Preview for invoice {invoice_id}",
        republic.Image("image/png", url="https://example.test/invoice.png"),
    ])
```

Media results feed the current model input; they are not a media persistence solution. For audit or replay, the host stores the file and records a resolvable reference in its business records.

## Inject per-Run context {#tool-context}

Use `ToolContext` when a tool needs the session name, request-scoped permissions, or event bus. Bub injects it, and it is excluded from the model-visible argument Schema:

```python
from bub.core.tools import ToolContext, tool


@tool(context=True)
async def add_order_note(note: str, *, context: ToolContext) -> str:
    """Append an order note to the current session."""
    await context.tape.append_event(
        "order.note",
        {"text": note, "request_id": context.state.get("request_id")},
    )
    return f"Note recorded in session {context.tape.name}"
```

Pass the state for this Run:

```python
async with agent.run(
    prompt,
    model=model,
    tape="customer-42",
    state={"session_id": "customer-42", "request_id": "req-01"},
) as stream:
    ...
```

`context.state` is shared only within the current Run and is not restored automatically. `append_event()` appends a historical record, but ordinary business events are not included in the next model input by default; include them deliberately through context projection when the model needs them.

## Sync functions, async functions, and concurrency {#concurrency}

A model can request several tools in one response. `Agent(max_tool_concurrency=...)` limits concurrency for **that batch of calls**: `None` is unlimited and `1` executes in order. It is not an application-wide rate limiter.

Synchronous tool functions run directly on the current event loop. Wrap blocking database drivers, file processing, or third-party clients in a thread so they do not stall unrelated requests:

```python
@tool
async def export_order_report(order_id: str) -> str:
    """Build an order report and return its download URL."""
    return await asyncio.to_thread(build_report_blocking, order_id)
```

`async def` does not make blocking code non-blocking; use genuinely asynchronous I/O or explicitly offload the work.

`Agent(tools=[...])` also accepts provider tools such as `republic.tools.WebSearch()`. The model provider executes those tools without the local `ToolExecutor`, so local `max_tool_concurrency` does not limit them.

## Call a tool without a model {#call-a-tool-without-a-model}

For a deterministic command entry point, set `command_prefix` on the Agent. Commands use the same tool implementation and argument validation without calling the model:

```python
agent = Agent(tools=[get_order], command_prefix=",")

async with agent.run(",get_order A123", model=model, tape="customer-42") as stream:
    async for event in stream:
        if event.kind == "text":
            print(event.data["delta"], end="")
```

Direct commands emit `CommandFinished` and a text result, not `RunStarted` / `RunFinished`. Command errors go directly to the caller instead of back to a model for self-correction. Permission policies that must cover command paths still belong in `ToolCallStarted`.

## Advanced: compose tools with Code Mode {#compose-tools-with-codemode}

With many tools or a piece of conditional logic, the model can use `run_code` to write Python that composes several tools in one execution:

```python
from bub.core.codemode import CodeMode

code_mode = CodeMode([get_order])

agent = Agent(
    tools=[code_mode.run_code],
    system_prompt=[
        "Use the available tools; you can write Python that calls tools.*.",
        code_mode.prompt,
    ],
)
```

Model-written code can then call:

```python
order = await tools.get_order(order_id="A123")
print(order)
```

### Choose an execution environment {#choose-an-execution-environment}

`Environment` defines contracts for process creation, file access, code execution, and shutdown. The default `LocalEnvironment` starts a Python process on the host; remote or isolated environments can provide different filesystem, network, and permission boundaries.

:::caution
**A separate process is not a security sandbox.** Do not treat host execution of untrusted model code as a security boundary. Configure an `Environment` with explicit filesystem, network, and permission isolation when required; see the [Python API](/docs/reference/python-api/) for the complete protocol.
:::

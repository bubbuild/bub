A turn is one inbound message, and all the work that it causes. `BubFramework` handles a turn: it finds the session, loads the state, builds the prompt, runs the model, and delivers the reply. Each stage has a hook, so a plugin can change that stage.

A turn belongs to `bub[app]`. A direct `core.Agent.run()` call has no turn. The loop starts with the prompt, state, and tape that you give it.

## Stages

`framework.process_inbound(message)` runs these stages in order:

| Stage | What it does |
| --- | --- |
| `resolve_session` | Select the session ID for the inbound message. |
| `load_state` | Collect the turn state from the hook implementations. |
| `build_prompt` | Turn the inbound content into a prompt. |
| `run_model` / `run_model_stream` | Produce the model output, as a final result or as a stream. |
| `save_state` | Finish the work of the model stage. This stage runs in its `finally` block. |
| `render_outbound` | Turn the result into outbound envelopes. |
| `dispatch_outbound` | Deliver each outbound envelope. |

The built-in plugin supplies the app defaults. Other plugins can add behavior or replace it, as each hook's contract allows. The [hooks reference](/docs/reference/hooks/) defines the first-result hooks, the combined results, and the priority rules.

## Agent call

The built-in `run_model_stream` hook calls `BubAgent.run_stream()`. `BubAgent` uses the core model and tool loop. It adds settings, skills, commands, steering, and the app tool policies.

The framework converts between streaming and non-streaming hook results. `process_inbound(..., stream_output=True)` lets the channel router read the output as it arrives. It returns a complete `TurnResult` when the stream ends.

A plugin can replace `run_model` and change this behavior. For example, an echo plugin can return text without an agent run. Core events and tape records occur only when the chosen implementation uses the core agent.

## Resources and failures

Use `async with framework.running():` when your hooks provide stores or other app resources. This opens the resources and releases them on exit. The built-in per-message lifespan opens during state loading and closes in `save_state`.

`save_state` runs when execution reaches the model stage. It also runs when that stage raises an exception. A failure in session resolution, state loading, or prompt construction occurs before the `finally` block, so it does not run `save_state`. If your plugin gets resources in those earlier stages, release them yourself.

The built-in `save_state` closes the per-message lifespan. The app saves selected settings in a different place. To save other state, add your own persistence policy.

If the model stage raises an unhandled exception, the framework runs `save_state`, then skips rendering and dispatch. The outer error path calls `on_error(stage="turn", ...)` and raises the exception again. The built-in error observer can send an error reply through outbound dispatch. A failure in one `on_error` observer does not stop the other observers.

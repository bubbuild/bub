An agent needs two things. It needs a record of its work. It also needs a useful set of messages for the next model call. Bub keeps the record in a tape. It builds the model context from the entries that you select. Because these are separate, you can keep the full history and still send a short request.

`core.Agent` and `BubAgent` share this model. Their default stores and session names are different.

<a id="storage"></a>

## Storage

A plain `Agent` creates an `InMemoryTapeStore` by default. That history lives as long as the store. To keep it between processes, pass a file store:

```python
from pathlib import Path

from bub.core import Agent
from bub.core.store import FileTapeStore

agent = Agent(store=FileTapeStore(Path("sessions")))
```

Each `agent.run(..., tape="customer-42")` uses the named tape in that store. Use the same name to continue a conversation. Use another name to keep conversations apart. `Agent` uses the name as given. The app has its own workspace and session naming.

`agent.tape(name)` gives you a view of a tape outside a run. Its writes go straight to the store:

```python
async def inspect_history() -> None:
    tape = agent.tape("customer-42")
    messages = await tape.read_messages()
    entries = list(await tape.query().all())
    print(len(messages), "model messages;", len(entries), "stored entries")
```

To use your own store, implement `TapeStore` or `AsyncTapeStore` from `bub.core.store`. Pass the instance as `Agent(store=my_store)`.

| Method | What it does |
| --- | --- |
| `list_tapes()` | Return the names of the stored tapes. |
| `fetch_all(query)` | Return the entries that match the `TapeQuery`, with its filters and order. |
| `append(tape, entry)` | Append an entry to the named tape. |
| `reset(tape)` | Clear the named tape. |

Use synchronous methods for `TapeStore` and asynchronous methods for `AsyncTapeStore`. The agent adapts a synchronous store for async use. Your store and your app handle persistence and coordination between processes.

<a id="context"></a>

## Context

Tape entries are messages, tool calls, tool results, events, and anchors. Normal recording only appends entries. To clear history, call an explicit operation such as `Tape.reset()`.

The default `TapeContext` selects the conversation entries after the latest anchor. It then converts them to Republic messages:

| Entry | Model context |
| --- | --- |
| `anchor` | The default query leaves it out. If a custom query selects anchors, the default selector converts them to assistant messages. |
| `message` | The saved message. |
| `tool_call` | An assistant message that carries the calls. |
| `tool_result` | Tool messages, paired with the calls before them. |
| Other events | The default selector leaves them out. |

An anchor marks a new starting point for the context. `handoff()` writes one and keeps the earlier entries:

```python
async def start_next_phase() -> None:
    await agent.tape("customer-42").handoff(
        name="order-reviewed",
        state={"summary": "Order A123 has shipped; the customer needs tracking details."},
    )
```

This `state` is saved on the anchor, before the starting point of the default query. To carry a summary into the next phase, put it in the next prompt or select it in your context strategy. To load values back into the run's mutable state, write your own loader. A new session gets a `session/start` anchor automatically.

To choose another anchor, pass `context=TapeContext(...)` to `Agent`. You can also use your own `select(entries, context)` function. A selector returns Republic messages, or an awaitable of them. `default_tape_context()` includes tool exchanges. A bare `TapeContext` without `select` uses the simpler message-only conversion. Entries marked `context=False` are removed before either selector runs.

When the agent recognizes a context-length error, it makes one automatic handoff. It then retries the prompt with the shorter context. If you need a summary of the earlier history, create it before the handoff. The retry can still fail if the request is too large.

<a id="state"></a>

## State

The `state` that you pass to `agent.run()` is a mutable dictionary. Tools, prompt sections, and event handlers share it during the run. Your app owns its persistence. Keep durable data in your own store, or write selected facts to the tape and read them back when you need them.

The default [TapeRecorder](/docs/concepts/events/#recording) saves conversation exchanges and selected lifecycle records. To keep other variables, custom events, or decisions, record them yourself.

<a id="forks"></a>

## Forks

Each `agent.run()` opens a fork of its tape. When the stream closes, the fork appends its new entries to the parent tape. This also happens after an exception or an early cancellation. A failed run can therefore leave useful partial history.

Pass `merge_back=False` to discard the records of the fork on exit. This affects tape writes only. Tool side effects, such as a sent request or a changed file, stay.

For a block of work that you control directly, use `agent.session(name, merge_back=...)` or `tape.fork_tape(merge_back=...)`. Both merge on exit by default, including exits with an exception.

If two runs share a tape and must see each other's completed work, serialize them. Your app provides the session lock. The [FastAPI example](/docs/sdk/web-service/) shows locking in one process. Multiple workers need coordination between processes.

## Sidecars

A `TapeSidecar` stores related data in a separate tape. A mounted sidecar follows the main tape through forks, merges, and resets. Its entries stay out of the main context. Pass sidecars to `Agent(sidecars=...)` when your app needs them.

The Bub app mounts a spill sidecar for large tool results. It keeps a short preview and a handle in the conversation. The agent can then read parts of the result with `spill.read`. If a sidecar fails during a fork merge or a tape reset, the app records the failure separately. The main tape operation can still complete. The spill limits are in the [app configuration](/docs/app/configure/).

<a id="application-storage"></a>

## App storage

`BubAgent` uses the store that `BubFramework` provides. The built-in app uses `FuzzyFileTapeStore` under the Bub home directory, normally `~/.bub/tapes/`. The tape name combines hashes of the workspace path and the session ID. The same session ID in two workspaces therefore has two separate histories.

To replace the store, an app uses `provide_tape_store`. To select the context, it uses `build_tape_context`. The [SQLAlchemy guide](/docs/integrations/storage/) shows this plugin route. For a direct SDK service, pass your implementation to `Agent(store=...)` as shown above.

The built-in app restores selected session settings from tape records. Other turn-state values need their own persistence.

Before choosing an extension point, first consider whether you are adding an action, operating instructions, or a change to how a run works. Different extension points can be combined, but the same rule should have only one implementation.

## Choose by goal {#choose}

| Goal | Extension point | How to connect it |
| --- | --- | --- |
| Query or modify an external system | [Tool](/docs/sdk/tools/) | `Agent(tools=[...])`, or the app's `provide_tools()` |
| Give the Agent a set of reusable operating instructions | [Skill](/docs/app/skills/) | A workspace skill directory, or shipped with a plugin package |
| Hand an independent subtask to another Agent to run | [Subagent](/docs/app/subagents/) | The built-in `subagent` tool, which can restrict the session, model, tools, and skills |
| Observe, rewrite, or block model and tool calls | [Agent events](/docs/concepts/events/#call-control) | `agent.events.on()`; app plugins use interception hooks |
| Change how history is converted into model messages | [TapeContext](/docs/concepts/tape/#context) | `Agent(context=...)`, or `build_tape_context()` |
| Replace history storage | [Storage integration](/docs/integrations/storage/) | `Agent(store=...)`, or `provide_tape_store()` |
| Replace the model client or execution environment | Core components | Constructor arguments; the app environment uses `provide_environment()` |
| Change message preparation, state saving, or reply sending | [Application hooks](/docs/app/hooks/) | A plugin implements the corresponding Turn hook |
| Connect a new messaging platform or backend service | [Channel](/docs/app/gateway/) | Implement Channel and provide it through `provide_channels(message_handler)` |
| Make an extension take effect automatically once installed | [Plugin](/docs/app/plugins/) | Register it in the `bub` entry point group |

For example, an order plugin can provide:

- tools to query and modify orders;
- a skill describing the after-sales process;
- an interception hook that checks permissions before an order is modified;
- a Tape handler that saves order events.

They handle execution, process, constraints, and recording respectively; there is no need to cram all four kinds of logic into one function.

## Kernel assembly and app discovery {#kernel-and-app}

The core layer is assembled explicitly by the caller:

```python
agent = Agent(
    model=model,
    tools=[order_tool],
    store=store,
    context=context,
)
```

The application layer assembles the same kinds of components through hooks such as `provide_tools`, `build_tape_context`, and `provide_tape_store`, and then `BubFramework.load_hooks()` loads the built-in implementations and installed plugins.

The choice rests on **who is responsible for assembly and lifecycle**:

- Embedding into an existing service, where the host manages dependencies and resources: use the core-layer constructor arguments.
- Wanting an extension to take effect automatically after installation, or distributing it to others: use an application plugin.

When using core components directly, you can also integrate [application plugins](/docs/sdk/reuse-plugins/) as needed.

## Tools and skills {#tools-and-skills}

A tool is a type-annotated Python function that performs an action. A skill is a directory containing `SKILL.md` and supporting files that tells the model how to complete a class of tasks.

| Dimension | Tool | Skill |
| --- | --- | --- |
| Content | Python functions and a parameter schema | Markdown instructions and supporting files |
| Purpose | Execute code and access external systems | Define processes, constraints, and operating methods |
| Loading | The available tools are provided on every model call | Each step lists names and descriptions; the body is expanded when the skill is referenced |
| Distribution | Passed directly to the Agent, or registered by a plugin | Placed in the workspace, or distributed with a package |

Scripts in a skill do not run automatically just because the files exist. When code needs to run, it still happens through a tool call; the skill can guide the model on when to call it.

The same tool can be called directly by the model, called by Python generated in code mode, or called through a [text command](/docs/sdk/tools/#call-a-tool-without-a-model). All three paths share the handler and parameter validation, but their output and error behavior can differ.

## Messages, state, and records {#messages-and-state}

| Object | Responsibility | Lifetime |
| --- | --- | --- |
| `Envelope` | Carries message content, routing, and session information | One inbound or outbound message |
| `TurnState` | Shares this round's data between hooks, tools, and event handlers | One Turn or Run |
| Tape | Saves the conversation, tool round-trips, and explicitly written records | Determined by storage; can span Turns and processes |

New message sources produce an `Envelope` through a Channel. Data used only in the current Turn goes into `TurnState`; long-term facts are written to the Tape or to application storage. Not every hook receives `TurnState`; when you need state, declare the parameter according to the corresponding signature.

## Reviewing an extension design {#one-owner}

Before implementing, make these boundaries clear:

- **A rule has only one authoritative source**: domain constraints are guaranteed by the tool or the domain layer; a unified policy can live in a hook, but do not maintain two judgments that may diverge.
- **Each kind of instruction has its own purpose**: `AGENTS.md` provides workspace rules, while skills provide task instructions that are expanded on demand.
- **Context is not concatenated twice**: `TapeContext` selects history, and `build_prompt` prepares the current input.
- **Errors have a definite destination**: decide whether an exception should propagate, be logged and skipped, or be converted into a tool result.
- **Resources have an owner that closes them**: make the lifecycle of connections and streams explicit, and decide how concurrent runs in the same session coordinate.

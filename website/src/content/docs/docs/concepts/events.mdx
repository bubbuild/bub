title: Events

Every Agent has an event bus (`EventBus`). Register handlers through `agent.events` to record a run, or to make a decision before a model or tool call.

## Telling the three kinds of data apart {#three-kinds}

| Type | Purpose | How to access it |
| --- | --- | --- |
| `AgentEvent` | Observe the lifecycle and control model and tool calls | `agent.events.on(...)` |
| `StreamEvent` | Deliver text, tool progress, usage, and errors to the caller | Iterate the stream returned by `agent.run()` |
| `TapeEntry` | Save the conversation and some run records | Query the [Tape](/docs/concepts/tape/) |

The three kinds of data flow in different directions:

- Modifying mutable fields of an `AgentEvent` can affect subsequent execution.
- A `StreamEvent` is only an output payload. Iterating drives the model loop; closing the stream ends a run that has not finished.
- A `TapeEntry` is for later queries and does not change the Step that is executing; only entries selected by `TapeContext` become input for later model calls.

## Registering handlers {#handlers}

```python
from bub.core.events import StepFinished, ToolCallFinished


@agent.events.on(ToolCallFinished)
async def report_tool(event: ToolCallFinished) -> None:
    print(event.call.tool, event.result.duration_ms, "ms")


def report_step(event: StepFinished) -> None:
    print("step", event.step, event.status)


agent.events.on(StepFinished, report_step)
agent.events.off(StepFinished, report_step)  # remove it when no longer needed
```

The decorator and passing the function directly are equivalent. A handler registered on a base class also receives subclass events; listening to `AgentEvent` handles all Agent events uniformly.

### Delivery rules {#delivery}

1. Each `emit()` calls the matching handlers in registration order.
2. When a handler returns an awaitable, the bus waits for it to finish before calling the next one.
3. Return values are ignored; to control the run, modify the event's fields.
4. Exceptions propagate to the caller of `emit()` and may fail the run.
5. Before each handler runs, `event.stopped` is checked; when it is `True`, this dispatch stops.

Handlers used only for logging or metrics should handle their own exceptions so they do not affect the main flow. The ordering guarantee applies only within a single `emit()`; when concurrent tools or multiple Runs share state, the caller still has to coordinate.

## Controlling model and tool calls {#call-control}

`decision` is used to skip the original call; other mutable fields are used to replace the request, arguments, result, or subsequent messages. For example, forbid an order modification that lacks permission before it runs:

```python
from bub.core.events import ToolCallDecision, ToolCallStarted


@agent.events.on(ToolCallStarted)
def check_order_update(event: ToolCallStarted) -> None:
    if event.call.tool != "update_order":
        return
    if not event.state.get("orders_writable"):
        event.decision = ToolCallDecision.deny("This session does not allow order changes.")
```

`ToolCallStarted` supports three ways to take control:

| Action | Is the tool executed? | Result | Subsequent handlers |
| --- | --- | --- | --- |
| `deny(message)` | No | A tool error | Dispatch stops |
| `replace(result)` | No | The specified result | Dispatch stops |
| Replace `event.call` | Yes, with the new call | The actual execution result | Dispatch continues |

A denied or replaced tool still emits `ToolCallFinished`. The model loop returns the error to the model as a tool result; a direct command raises the error to the caller.

The event itself is a mutable dataclass, but payloads such as `event.call` and `event.request` are frozen objects. When replacing arguments, create a new payload with `dataclasses.replace()` instead of modifying fields in place.

Setting `event.decision = LLMCallDecision.finish(text)` on `LLMCallStarted` skips the model provider and produces text directly. In that case no corresponding `LLMCallFinished` is emitted.

## Recording conversations and custom events {#recording}

The Agent registers `TapeRecorder` before your handlers. The recorder subscribes to `RunStarted`, `RunFinished`, `StepStarted`, `StepFinished`, `ChatFinished`, and `CommandFinished`.

Among them, `ChatFinished` saves the conversation and tool round-trips, and later model calls build their context from these records. Tracing and Tape recording are independent of each other; turning tracing off does not stop recording.

Custom events inherit from `AgentEvent`, or from `TapeEvent` when they need the current Tape:

```python
from dataclasses import dataclass

from bub.core.events import TapeEvent


@dataclass(kw_only=True)
class OrderReviewed(TapeEvent):
    order_id: str


@agent.events.on(OrderReviewed)
async def record_review(event: OrderReviewed) -> None:
    await event.tape.append_event("order.reviewed", {"order_id": event.order_id})


async def mark_reviewed() -> None:
    tape = agent.tape("customer-42")
    await agent.events.emit(
        OrderReviewed(state=tape.context.state, tape=tape, order_id="A123")
    )
```

`TapeRecorder` does not record custom events automatically; the example above writes one explicitly in a handler. Custom events also have no built-in `decision` protocol; when you need to return a result, define mutable fields yourself, and when you need to stop dispatch early, override the `stopped` property. Tools can emit events through `context.events`.

## Using hooks in the app {#app-plugins}

`AgentPlugins` connects application hooks to Agent events:

| Application hook | Agent event |
| --- | --- |
| `before_llm_call` / `after_llm_call` | `LLMCallStarted` / `LLMCallFinished` |
| `before_tool_call` / `after_tool_call` | `ToolCallStarted` / `ToolCallFinished` |
| `continue_prompt` | `StepFinished` |
| `provide_steering_inbox` | `MessagesPending` |

Steering injects supplementary messages into later model requests of the current Run through `MessagesPending`. It differs from queueing: queued messages wait until the current Turn ends. The event layer provides the injection point; admission and queueing policies are decided by the channel and the application.

`BubAgent` uses this adapter by default, and a core Agent can also [connect it explicitly](/docs/sdk/reuse-app/#other-hooks).

The two ways of connecting have different exception policies: exceptions from direct EventBus handlers propagate to the publisher, while exceptions from interception hooks are logged and skipped. To reject a call, return the corresponding decision. For full signatures, see the [Hooks reference](/docs/reference/hooks/#interception-through-pluginagenthooks); for examples, see [Application hooks](/docs/app/hooks/).

`framework.events` is another, independent bus that publishes only the application-level `CommandChanged`, `WorkChanged`, and `PromptChanged`; it does not carry model-call or channel events.

## Event reference {#event-reference}

| Event | When it fires | What can be read or modified |
| --- | --- | --- |
| `RunStarted` | A model Run starts | `model`, `prompt`, `metadata` |
| `RunFinished` | The Run's stream closes | `status`, `steps`, elapsed time, and error |
| `StepStarted` | A Step starts | `step`, optional `prompt` |
| `StepFinished` | A Step ends | Progress and usage; set `next_prompt` to continue |
| `MessagesPending` | While building a request, or when a particular Step ends | Append user content to `messages` |
| `LLMCallStarted` | Before calling the model provider | Replace `request`; set `LLMCallDecision.finish()` |
| `LLMCallFinished` | The provider call succeeds or fails with an ordinary exception | `request` and the aggregated `result` |
| `ToolCallStarted` | Before a tool runs | Replace `call`; set `deny` or `replace` |
| `ToolCallFinished` | A tool succeeds, fails ordinarily, is denied, or is replaced | Assign to `event.result.result` to replace the result |
| `ChatFinished` | When the current Step's conversation and tool round-trips can be recorded | Messages, tool round-trips, usage, and errors |
| `CommandFinished` | A direct command succeeds or fails | Command, status, and output |

`RunFinished` is emitted when the stream closes; a Run closed before it is iterated ends as `cancelled` with zero Steps. The Finished events for models and tools are not guaranteed to cover cancellation paths, so billing and cleanup cannot rely on them alone.

`StepFinished.next_prompt` sets the next Step's user message, and `MessagesPending.messages` receives messages that arrived during the run. When `BUB_MAX_STEPS` is reached, the run raises a `max_steps_reached` error.

A direct command emits tool events and `CommandFinished`, but no `RunStarted` / `RunFinished`. Every Agent event has `state`; subclasses of `TapeEvent` also carry the current `tape`.

Agent events let you watch a run. They also let you decide before a model or tool call. Every Agent creates an `EventBus` and subscribes a `TapeRecorder`. You add handlers through `agent.events`.

Three kinds of information have three different jobs:

| Type | Job | How to read it |
| --- | --- | --- |
| `AgentEvent` | Lifecycle of the run and interception of calls. | `agent.events.on(...)` |
| `StreamEvent` | Output for the caller, such as text and tool progress. | Iterate over the stream that `agent.run()` returns. |
| `TapeEntry` | The saved conversation and selected runtime records. | Query the [tape](/docs/concepts/tape/). |

The agent loop controls execution. It calls the event handlers at fixed points, before it continues. TapeRecorder saves selected exchanges and lifecycle records. Your handlers can record the other events that you need to keep.

<a id="delivery"></a>

## Handlers

This example uses the `agent` from the [SDK guide](/docs/sdk/):

```python
from bub.core.events import StepFinished, ToolCallFinished


@agent.events.on(ToolCallFinished)
async def report_tool(event: ToolCallFinished) -> None:
    print(event.call.tool, event.result.duration_ms, "ms")


def report_step(event: StepFinished) -> None:
    print("step", event.step, event.status)


agent.events.on(StepFinished, report_step)
```

To remove a handler, call `agent.events.off(StepFinished, report_step)`. A handler for a base class also receives its subclasses. A handler for `AgentEvent` receives every agent event that is delivered.

For each emission, the matching handlers run in the order of registration. The bus waits for each async handler before it starts the next one. The bus ignores the return value of a handler. An exception goes to the caller of `emit()` and can fail the run. If work must continue after an observer fails, catch the exception inside that observer.

This order applies to one emission. Concurrent tool calls or runs can emit events at the same time. Shared handler state therefore needs its own coordination.

<a id="control"></a>

## Call control

To stop a call, assign a decision to the `decision` field of the event:

```python
from bub.core.events import ToolCallDecision, ToolCallStarted


@agent.events.on(ToolCallStarted)
def require_refund_permission(event: ToolCallStarted) -> None:
    if event.call.tool == "refund_order" and not event.state.get("refunds_allowed"):
        event.decision = ToolCallDecision.deny("Refunds require approval.")
```

`deny()` skips the tool and produces a tool error. `replace(result)` skips the tool and supplies a result. Both stop delivery to the later handlers of that `ToolCallStarted` event. The executor still emits `ToolCallFinished` for the outcome. A model loop receives the error as a tool result. A direct command gives the error to its caller.

To change the arguments and continue, replace `event.call` with `dataclasses.replace(event.call, arguments=...)`. To finish before a model call, set `event.decision = LLMCallDecision.finish(text)` on `LLMCallStarted`. This stops the later handlers and skips the provider call. A skipped provider call does not emit `LLMCallFinished`.

| Event | When it occurs | What you can do |
| --- | --- | --- |
| `RunStarted` | A model run begins. | Read the prompt, the model, and the metadata. |
| `RunFinished` | The stream of the run closes. | Read the status, the step count, the elapsed time, and the error. |
| `StepStarted` | A model step begins. | Read the progress. |
| `StepFinished` | A model step ends. | Read the progress. When `status == "continue"`, set `next_prompt` to give the next step a user message. |
| `MessagesPending` | A step builds its model request, or ends without tool calls. | Append user messages to `messages`. They come before the next prompt. Messages that you add at the end of a step continue the run. |
| `LLMCallStarted` | Before a provider call. | Replace `request`, or set `LLMCallDecision.finish(text)`. |
| `LLMCallFinished` | A provider call completes, or fails with an exception. | Read the accumulated result. This event does not report a cancellation or a close by the consumer. |
| `ToolCallStarted` | Before a tool runs. | Replace `call`, deny the call, or replace the result. |
| `ToolCallFinished` | A tool succeeds, fails, is denied, or is replaced. | Assign `event.result.result` to change the returned result. |
| `ChatFinished` | The exchange of a step is ready to record. | Read the exchange. |
| `CommandFinished` | A direct command finishes or fails. | Read the command, the status, and the output. |

Command prompts run tools directly. They emit tool events and `CommandFinished`. See [Commands](/docs/sdk/tools/#commands).

All agent events carry the turn `state`. Events that derive from `TapeEvent` also carry the active tape. For tool events, the tool context is available as `event.call.context` when the call has one.

<a id="recording"></a>

## Recording

The Agent registers TapeRecorder before your handlers. It records `RunStarted`, `RunFinished`, `StepStarted`, `StepFinished`, `ChatFinished`, and `CommandFinished`. The `ChatFinished` handler writes the messages and tool exchanges that later model calls read as context.

Recording is part of normal operation. It writes to the configured store. That store is in memory unless you supply another one. Recording does not depend on the tracing configuration.

To save a custom event, add a handler that writes it to the tape. Use the interception events to change a request or a result. A `ChatFinished` observer runs after the default recorder has saved that exchange.

<a id="custom-events"></a>

## Custom events

Define a dataclass that derives from `AgentEvent`. Derive it from `TapeEvent` when the handlers need a tape. This example records a business event:

```python
from dataclasses import dataclass

from bub.core.events import TapeEvent


@dataclass(kw_only=True)
class OrderReviewed(TapeEvent):
    order_id: str


@agent.events.on(OrderReviewed)
async def record_review(event: OrderReviewed) -> None:
    await event.tape.append_event("order.reviewed", {"order_id": event.order_id})


async def mark_reviewed() -> None:
    tape = agent.tape("customer-42")
    await agent.events.emit(
        OrderReviewed(state=tape.context.state, tape=tape, order_id="A123")
    )
```

`emit()` returns the event after the handlers have run. A custom mutable event can carry a response back to its emitter. Override its `stopped` property if delivery must end when that response is set. Tools can emit events through `context.events`, with the same turn state.

<a id="application-hooks"></a>

## App plugins

`AgentPlugins` connects four hooks to the call events: `before_llm_call`, `after_llm_call`, `before_tool_call`, and `after_tool_call`. It connects the `continue_prompt` hook to `StepFinished`. It connects the steering inbox to `MessagesPending`. A plugin returns the values that the hook contract requires, and the adapter updates the event. `BubAgent` uses this adapter, and a core Agent can [use it too](/docs/sdk/app-plugins/#agent-plugins).

This adapter follows the plugin hook order. It catches exceptions from individual interception hooks, logs them, and skips them. To deny a call, return the correct decision. The other app hooks follow their own error contracts.

See [Change application behavior](/docs/app/hooks/) for plugin examples. For order and signatures, see [Application hooks](/docs/reference/hooks/). EventBus is part of the base SDK installation.

`framework.events` publishes commands, channel work, and user prompts. It uses `CommandChanged`, `WorkChanged`, and `PromptChanged` from `bub.application`. You subscribe and unsubscribe with the same `on()` and `off()` API.
